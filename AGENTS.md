The GitHub ledger must distinguish banked work from workspace-only progress. Link the commit containing a regression or correction once pushed; until then label it workspace-only and pending banking. A banked fix remains pending verification until its stated gates and independent review complete. Never describe uncommitted work as part of a downloadable build.

- Make changes and prepare new versions on a feature branch, never directly on `main`.
- Verify the work and open a draft pull request so the user can review and test it.
- Establish bug fixes through meaningful automated evidence. Reproduce the defect with a regression that fails before the fix and passes afterward, exercising the real owning behavior and relevant boundary, failure, race or recovery cases. Use unit tests for isolated logic and integration/browser tests when the defect crosses those boundaries; do not substitute implementation-shaped assertions or a passing suite count for proof. A sufficiently verified internal defect can be closed without requiring the user to reproduce an impractical timing or failure scenario. Reserve manual acceptance for evidence automation cannot establish, and state that limit precisely.
- Complete the agreed comprehensive bug-hunt scope before advancing the candidate. Track reviewed areas and remaining coverage alongside the bug ledger; a successful first batch of fixes is a checkpoint, not completion of the whole review. Continue through confirmed defects and concrete coverage gaps without reopening closed performance decisions or making speculative refactors.
- Provide the successful GitHub Actions test-build download when handing over a feature for in-app review.
- Chrome (Blink) and Firefox (Gecko) are required browser targets. Before handing over a build, keep both browser gates passing and verify new or changed UI flows in both engines, including relevant cold navigation, loading/recovery and viewport behavior. A Chrome-only pass does not establish Firefox compatibility. Record the actual coverage and any manual checks in the handoff; see [browser validation](docs/VALIDATION.md#browser-compatibility).
- Do not push changes into `main` or merge a pull request until the user explicitly approves after review.
- Bug fixes and general performance work should be invisible to the user: preserve intended behavior, workflows and presentation. Do not add in-app notices, warnings, status text, extra clicks or controls explaining a bug, repair, optimization or internal workaround. Keep implementation explanations and verification evidence in the bug ledger, development notes and review handoff. New user-facing messaging needs a separate product reason that helps the user understand meaningful application state or make a decision; fixing an internal defect alone is not that reason.
- Preserve verified performance improvements when fixing correctness. Prefer bounded changes in the owning code; do not restore repeated full-history reads, redundant polling, broad invalidations or other retired costs as a convenient workaround. Verify the affected cost or request bound when a fix could change it, and record the evidence beside the correctness regression.
- Review every fix independently before accepting it into the validated candidate. Review the actual owning behavior, regression quality, failure/recovery boundaries and affected performance costs; record the reviewer and disposition. Review does not replace the required automated gates. Apply the same standard when retrospectively checking earlier fixes, without interrupting current authorized work.
