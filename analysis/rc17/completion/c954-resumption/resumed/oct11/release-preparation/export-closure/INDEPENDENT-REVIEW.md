## Scope and source mapping

The original RC16 follow-up methodology explicitly requires both a complete before/after export field/record comparison and a pre-upgrade database reopened twice. This bounded synthetic control closes that existing observation gap without reopening an optimization decision. It does not claim an installed-user upgrade or an unsupported history-export/import round trip.

The review read the complete worker, runner and README, the actual RC16 and source70 `/api/export` routes and authentication/broadcast routing, Store migration/schema owners, Universe export/navigation/politics owners, and transport-retention initialization. The reused process Envelope and provenance helpers were also inspected. The README's three relative source-methodology links resolve.

The worker creates its fixture with actual RC16 Store/Core, confirms the pre-upgrade travel marker/column are absent, and uses four real application lifecycles: RC16, source70 upgrade, and two subsequent source70 reopens. Every one of the 24 declared retained SQL tables must contain rows. Selected rows preserve tied visit times, IDs, sovereignty, separate pilot ownership, hidden links, active/ended sessions, retry metadata, settings and nested JSON text.

Complete HTTP bodies are checked against SQL rows and explicit fixture values without calling the application's export helper. A before/after SQL check also prevents route-side mutation from being silently accepted by that oracle. All nested export sections remain in the full cross-version comparison. The only normalized response changes are validated ISO export time, version 8→9, the exact three discovered pilot/system memberships, asserted-null legacy `session_id`, and the exact new politics queue-version setting. Separate SQL checks assert the generated job value, three specific migration additions and bounded retention-grace metadata before comparing every selected old field/record. Both subsequent reopens require exact SQL equality and complete export equality apart from export time.

Six negative authentication/Origin/cross-site/broadcast requests are required in each lifecycle; the successful request obtains its cookie through the real dashboard route. The export must preserve its JSON, attachment and no-store headers and expose only the expected identity fields. Synthetic token sentinels must be absent from the exported body. External provider requests are denied. Nonexpiring fixture records and disabled provider polling keep this a preservation control; expiry behavior, real SSO and physical OBS remain outside its claim.

## Evidence finding resolved

The first version pinned early raw responses/expected bodies/SQL snapshots only after the whole worker finished. A file replacement during later lifecycles could therefore have escaped detection. Each evidence write now retains its original byte count/hash after exact read-back. The worker rechecks all closed pins before writing its result. The runner validates those pins and directly compares them with its final inventory, independently of the Envelope's closed-file pins. Both stopped synthetic directory inventories are also retained and checked. The original RC16 directory is byte-compared after all candidate lifecycles.

The runner rejects reused output, inherited Node instrumentation and unintended Kairo overrides; binds exact manifests to fresh-build receipts/logs; holds both established locks; and owns actual child exit/descendant drain. It freezes helpers, re-verifies source, checks temporary absence, and preserves failures and synthetic data. A startup failure without a returned lifecycle owner cannot be reported as cleanly closed.
