## Why retain it

The measured cost is approximately 0.17 ms for 100 credits and 1.07 ms for 10,000 credits per active goal. The actual Core call is after the relevant dataset refresh is stored; keyed goal selection keeps income evaluation on journal changes. Journal and industry jobs have a 300-second minimum/default supported interval, and mining has 600 seconds; source HTTP expiry can make those later. The `/goals` read path lists existing progress and does not execute this accumulator. Goal creation refreshes the pilot's active goals, and manual/forced sync paths can cause extra evaluations, so cadence is not a strict rate cap. Cadence informs frequency; each refresh still incurs its synchronous cost.

A maintained aggregate would add migration/import initialization and atomic ledger/total consistency obligations across the existing savepoint, baseline mining, decreased observations, clipping, rollback, reentrant creation and exactly-once completion. At the measured absolute costs and source-driven cadence, adding that state has no demonstrated RC17 benefit sufficient to justify the change. Existing shared source preparation, keyed lookups, change-aware writes and retained-credit reconciliation remain intact. This decision does not skip reconciliation, drop old credits, cache totals in memory, or relabel a changed implementation as measured.

## Limits and reopening condition

The 100,000-credit refresh is still a synchronous roughly 11 ms task. Many active goals are evaluated sequentially, so simultaneous large ledgers can accumulate blocking work; this lane measures one goal and does not establish an arbitrary goal-count bound or multi-pilot burst latency. Reopen the aggregate/index decision if a representative retained history and active-goal count produces material repeated blocking at actual refresh/creation cadence, or if the feature changes to evaluate totals on a hot read/UI path. This result does not close unrelated backend or full-system acceptance findings.
