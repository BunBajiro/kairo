The observed ~10–11-second conversions are well inside the 20-minute total and two-minute no-progress defaults. These samples do not measure hard native-memory ceilings; the 512 MiB old-generation and sampled 256 MiB external-allocation limits must not be described as RSS caps.

**U1 disposition at this source: measured; retain the default Worker/conversion architecture.** The actual loaded-app/restart evidence closes the previously missing measurement, including the adverse transient request sample. No demonstrated improvement supports a speculative compression-level, spool-strategy or representation rewrite in RC17; preserve its verified deterministic/integrity behavior. This is a bounded decision for the tested Linux environment, not a guarantee of Windows, slow-disk or browser/OBS latency. The final integrated source still needs its exact-source acceptance gate after the separate recovery fix is adopted.

## U3: inventory manifest decision

[Fresh inventory evidence](local-20261007/inventory.json) covers 25 service creations in one Node process with a warm filesystem. The six documents total **1,723,961 bytes**. First service readiness plus close took **13.82 ms**. The following 24 observations had median **8.81 ms**, p95 **12.47 ms**, maximum **15.88 ms**, and median CPU **9.19 ms**. This includes service state/cleanup reads; it is not an isolated JSON-parser timing or a cold-disk claim.

**Decision: retain the current inventory implementation; do not add a compact inventory manifest in RC17.** The cost occurs once per service activation and is small. These measurements establish the actual current cost, but do not establish a worthwhile gain from another generated metadata contract. This closes the conditional U3 design assessment without pretending an unimplemented manifest was benchmarked.

## U2/U2b recovery follow-up

The existing conversion watchdog, no-progress deadline, spool/output/external-allocation/free-space limits, worker-exit ordering and cleanup-warning implementation remain as recorded in [IMPLEMENTATION.md](IMPLEMENTATION.md). The actual archive completed within those production defaults.

An independent current-source review found one further recovery edge: rollback directly removed `pending.json` before selecting the valid active generation. A locked pending pointer could therefore abort rollback. [The isolated patch](rollback-recovery.patch) records the failed generation UUID durably before housekeeping, excludes that UUID from future preparation, retains visible cleanup errors, permits a fresh UUID for a manual retry of the same official build, and clears the marker after successful commit. Failure to write the rejection marker remains a visible recovery failure before cleanup.

The initial isolated patch passed **65/65** focused tests in [recovery-tests.log](local-20261007/recovery-tests.log). Parent review then found that ignoring an unreadable rejection-state file could revive the rejected UUID. The revised patch treats every rejection-state read failure except ENOENT as explicit failure, including malformed JSON, and preserves a previous failed UUID when an unrelated invalid pointer has no valid new identity. Additional regressions cover both cases; revised focused verification remains queued. Neither patch revision is part of the measured `c954c0d` source, and these loaded results do not substitute for its subsequent exact-source/CI gates.
