# F4 route delivery — measured no-change decision

**Reject the current lazy/Suspense trial. Keep the integrated RC17 routing unchanged.** The experiment establishes substantial deferred JavaScript delivery, but does not establish a cold Overview speed or CPU benefit on Kairo's loopback deployment. It adds a material delay to the first visit to deferred pages. A byte-only improvement does not meet the fluid-navigation objective.

This is a completed decision for the isolated proposal, not a clean RC17 readiness claim or a claim that all frontend work is closed. PR #10 remains withdrawn. No runtime change was applied.

Atlas and Maps share a module: the first of those routes pays its delivery/initialization cost. The two route orders expose this explicitly. Candidate Atlas requests 532,808 additional bytes when opened before Maps, versus its 1,185-byte worker script after Maps; Maps requests zero versus 497,956 bytes in the reverse order. These per-route midpoint values must not be interpreted as independent cold-route distributions.

A useful causal clue is OPSEC in the forward order: it requests **zero additional JavaScript bytes** after Studio but still takes 406.7 ms to become ready, versus baseline 145.0 ms. The dependency installation's React 19.2.6 production renderer contains a 300 ms fallback retry throttle (`react-dom/cjs/react-dom-client.production.js`, around line 10793). The observed delay is consistent with that scheduler path. This is a supported explanation, not a separate scheduler ablation; no claim that all first-visit cost is network or parsing is made.

Cold Overview settled-ready medians are 598.8 versus 591.1 ms, whereas visible-ready and task medians slightly favor baseline. With two observations and local transport, none supports a meaningful startup speed claim. The navigation cost is large and repeats across the deferred routes.

## Compiled correctness checks

All **28 checks across the four runs pass**, with zero recorded runtime exceptions. The candidate passes eight checks in each fresh run:

- Normal navigation preserves the document; back/forward restores route and selection.
- An unsaved mounted Studio draft survives source/context updates and is not published.
- Detached Atlas has its own browser target, a visible 778 × 384 canvas, loaded CSS, and restores to the workspace.
- The independently served OBS browser source renders the saved fixture.
- Delayed Markets delivery displays the loading state while shell navigation stays usable.
- A failed Markets import displays recovery; switching to another deferred page resets the failure boundary.
- Retrying returns to the same Markets hash using a new document/module map and completes successfully.

Baseline passes the five shared diagnostics and confirms it has no separate Markets chunk to fault. Candidate failure injection runs after all measurements, so its error/reload behavior does not contaminate timing.

## Disposition and integration

`integration-c954.patch` is retained as a **rejected experiment artifact**, and its applicability was checked against c954 without applying it. Do not apply that patch or merge the trial merely to close F4. The integrated source remains unchanged; no extra integration test is needed for a rejected code change.

The result rules out this specific simple route-boundary implementation as a performance improvement for the measured local workload. A future proposal could change loading/reveal behavior and repeat the same matched experiment, or reconsider deferred delivery for a remote deployment. Neither is required to pretend the present byte reduction improved local navigation. This result does not establish timings on the user's Windows/GPU machine, internet delivery, or populated Atlas/J-Space data; those remain outside this bounded F4 comparison.
