Prepared 11 October 2026 for the private `BunBajiro/kairo` analysis branch after GitHub Actions rejected an internal recovery artifact because its storage quota was full. This request is specifically authorized by the user. It is a storage maintenance action, not application validation or release acceptance.

The frozen request contains 124 existing artifacts, totaling **2,041,005,576 bytes**, from the 38 ordinary **Kairo test build** runs numbered **25–64 excluding 48 and 54**. Current build 65, RC16 build 48, selected build 54, every unlisted artifact, all internal performance/release artifacts, and all runs/logs are preserved. The five permitted names are `Kairo-test-build.zip`, its one paired `Kairo-test-build.sha256`, `session-interface-check`, `universe-interface-check`, and `datasets-interface-check`.

Request SHA256: `af6dd38ed523b35ac9471256536627979744cab4391c0cfe175eab2bbffe6f9c`. The implementation hard-pins this exact file hash. Its per-artifact records pin ID, digest, name, byte count, timestamps, expiry state, and full workflow-run identity; run records pin workflow, run number, source commit, branch, state and creation time. Root's read-only API inventories are the source of these records.

Publish the reviewed workflow as `.github/workflows/internal-artifact-cleanup.yml` and the script/request under `analysis/rc17/recovery-oct11/artifact-cleanup/` on the analysis branch. Root owns publication and execution. The workflow token has `contents: read` and `actions: write`; checkout does not persist credentials. No credential is printed, archived, or written into the request. REST requests use the fixed repository and canonical GitHub API origin without redirects.

The first workflow step validates every live run/artifact and prints the complete plan. The separate deletion step revalidates all identities before its first mutation and every artifact immediately before its deletion. Each attempt is logged before the DELETE request. Success requires HTTP 204 and a following HTTP 404 absence check. The final receipt records confirmed removals and any partial failure. These records are written to workflow logs because artifact upload itself is quota-blocked. A changed/missing target fails closed; rerunning this fixed request after partial/full deletion will also fail closed, rather than discover replacement targets.

Eight offline simulated controls passed with no network requests or live deletions. They verify exact scope, read-only planning, exact successful deletion IDs, changed-run/changed-artifact rejection before mutation, partial-progress preservation, protected/internal substitutions, and altered-plan rejection. Independent review and actual workflow outcome are recorded separately. GitHub's storage accounting may update later than successful deletion; removed bytes alone do not establish that new uploads already work.
