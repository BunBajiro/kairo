## Evidence controls

Every lane needs exact application/harness identity, environment, fixture counts and a completed outcome. Assert successful production results, correct owner/scope, expected content and actual completed workload counts. A fast rejected route, missing map, abandoned request, exited child or empty replay is a failed observation, not an optimisation.

Separate ordinary elapsed measurements from SQL/iteration tracing, forced garbage collection, heap snapshots, and diagnostic shutdown scheduling. Record which observer is in which process, and preserve production return/throw/async semantics when wrapping methods. Use a consistent clock or a documented clock relation for cross-process latency. Event count, simulated time and instrumented operation count are not measured CPU time.

Provider fakes are useful for repeatable eligibility/freshness/failure cases, provided requests pass through real Core/auth/ESI paths and attempts/results are counted. They do not establish live ESI service latency. Dashboard/OBS SSE protocol clients do not render the UI or run the actual OBS application. Record injected provider state separately from the state production accepted and published.

RSS is process-wide residency; heap after explicit GC is a diagnostic retained-heap snapshot. Neither a short increase nor incomplete RSS release alone proves a leak. Report warm-up, repeated-cycle, quiescent and post-GC observations separately, with history/cache growth and expected live objects accounted for. Do not force GC in ordinary latency windows.

## Refactoring responsibilities and acceptance

The implementation deliverable is a clearer ownership and data-contract structure as well as faster execution. File splitting alone is not a useful result.

| Current responsibility split | Target boundary | Concrete maintainability gain | Behaviour/measurement acceptance |
|---|---|---|---|
| Each map projection reloads per-pilot links, derives operations/signatures and performs reconciliation independently | One request-scoped projection context, with explicit pilot/map access boundary, bounded source time and grouped canonical records; selected detail and compact list have distinct contracts | One place defines snapshot consistency and data dependencies; callers do not unknowingly multiply materialisation | Same scope/access/expiry/signature meanings; no cross-pilot reuse; changed data and elapsed expiry remain visible; selected detail cost is largely independent of unrelated maps |
| Parent Universe refresh and Maps refresh respond separately to related events, using response epochs after work has already started | One owner coalesces matching scoped invalidation and schedules each necessary projection | Fewer competing request lifecycles and clearer revision ownership | Latest pilot/map/revision wins; queued edits, failure recovery, visibility wake, public-feed freshness and expiry remain correct |
| Every itinerary leg rebuilds route context and can carry unrelated lifetime history | One planning request prepares routing inputs once, with explicit policy/source dependencies and final current-connection validation | Route policy and data preparation stop being duplicated across legs | Equivalent routes, costs, warnings, ordering and scope; changes/expiry during planning handled; no global stale graph assumption |
| Semantic bus invokes asynchronous callbacks while teardown disposes listeners and closes storage without owning all accepted work | Explicit bounded quiesce/drain ownership before storage close, with cancellation/error policy and safe nested event semantics | One lifecycle contract tells each module when work is accepted, drained or aborted | Accepted history work has a documented disposition; rejected lookups visible; nested events do not deadlock; real supervisor restart/reconnect still works |
| Generic live map context couples lifetime visit aggregates to routing, display counters and historical discovery, while Sessions independently need time-bounded travel | Separate recording ledger, session timeline, historical discovery membership and optional display projections | Product removal can stop expensive display work without silently deleting session evidence | Lifetime counters disappear from ordinary views and route preparation; Sessions/replay/discovery remain intact; retired settings/bookmarks recover sensibly |
| `sessionReport` reads raw visits, then `sessionDetails` → `sessionRoute` reads the same owner/window again | One request-owned bounded travel read with explicit raw and route projections | One owner handles row ordering and query reuse without renaming or retaining an all-time history service | Preserve the raw compatibility list's inclusive end, the route's exclusive end and captured/legacy-inferred starting segment; report/replay callers request only needed projections |
| Cache and broadcast policy is scattered among consumers | Consolidate only measured redundant policy: idempotent writes, bounded replaceable caches, explicit shared snapshot/broadcast ownership | Fewer hidden invalidation/retention rules, without a schema-wide rewrite | Corrected source values and missed-event repair still propagate; durable history is not evicted; unchanged output does not cause unnecessary work |

Each implementation step should have an explicit contract change, targeted correctness checks and a before/after lane. Changes to output shape should compare preserved meaning rather than force byte identity across an intentional product retirement. No analysis harness, observer or artificial fixture belongs in RC17.

### Internal service contracts

Use ordinary in-process APIs. The aim is to let a caller request the capability it owns, without materialising a legacy feature or knowing its storage layout. No generic service framework, new network hop or blanket repository abstraction is needed.

| Service responsibility | Callers and explicit contract | Ownership and migration rule |
|---|---|---|
| Pilot observation acceptance | Current-location/OPSEC consumers, Maps tracking, discovery and session recording receive the pilot, source, observation time, freshness, system and ship evidence | Keep fresh/stale/disabled/disconnected distinctions. Snapshot acceptance and source baseline belong here; lifetime Journey presentation does not. Preserve the current per-pilot subscription and selected live-source rules. |
| Session movement and bounded travel queries | Session report, replay and combat preparation request an owned session and ordered time window, with explicit raw-row and derived-route outputs | Own new session movement recording, clipped start/end rules, repeated/equal-time observations, ship and recorded sovereignty. Reuse the window read inside reports, while preserving raw/route endpoint differences. Legacy rows are read through the same contract; no all-time aggregation is required to answer a session. |
| Remembered discovery membership | Atlas discovery consumers request per-pilot system identities, combined with their existing current/private/public sources | Store or derive identities without timestamps/counts if those have no retained purpose. Define one-time historical backfill and restart persistence. Do not rebuild a lifetime travel log under a new name. |
| Activity publication | Session timeline, Overview activity, dashboard changes and OBS toast rules consume typed semantic events | Make durable recording versus transient notification explicit. `core.publish` currently does both; callers must not accidentally restore outside-session travel history merely to show a toast. |
| Map read projection | Chooser asks for summaries; selected map asks for detail; commands return a current scoped projection | A request context owns canonical links/signatures/operations and one time reference. Grouping and revision/expiry checks are shared without leaking pilot/map scope. |
| Route input preparation | Single route and itinerary callers use the same policy/source context | Prepare once per request, reuse across legs, and revalidate mutable/expired connections before acceptance. No display aggregate or discovery ledger is an implicit route dependency. |
| Owned asynchronous tasks | Core/modules register accepted asynchronous work and close through quiesce/drain | Define which tasks finish, cancel, fail visibly or become retryable. Capture session/observation identity before awaited enrichment; storage closes after owned tasks settle within the shutdown policy. |
| Compatibility adapters | Existing documented Journey HTTP/export contracts and old saved settings | Keep adapters cold and explicit; migrate callers to retained services. A documented compatibility route does not justify running its old aggregate on each normal state load, nor require indefinite new lifetime collection. |

Production architecture/API documentation must describe the adopted contracts and caller ownership after implementation. In particular, `docs/ARCHITECTURE.md` still lists `server/modules/journey.mjs`, while RC16 actually registers `server/universe-history.mjs` from Core. ## Journey retirement: dependency and upgrade boundary

The intended product retirement is the standalone Journey log and lifetime counters/exploration progress. Existing session evidence is not disposable, but preserving it does not require preserving the whole deprecated Journey process. The user specifically asked whether future movement recording can belong to Sessions, with discovery retaining only system identities. The audit below identifies the remaining decisions and required migration; it does not declare a recording policy implemented.

### Display work that can be retired

- `components/kairo/universe.tsx`: `My footprint` preset; `Your visits` indicator option; non-replay lifetime visited-system highlighting; inspector visit count/last-visit display. Keep ordinary static system/security/ownership/navigation information.
- `components/kairo/universe-overview.tsx`: `Visited by you`, exploration percentage/progress, per-region visited counts and ordering driven by those counts. Choose an explicit remaining region order. Systems in view, geography, territory/activity and genuine discovery membership remain meaningful.
- `components/kairo/universe-map.tsx` and `universe-types.ts`: retire only non-replay visit-indicator branches and lifetime highlighting/type members. The `replay.trailSystemIds` path is distinct and must continue to paint historical travel.
- Restore old saved `indicator:'visits'` and `preset:'journey'` state to a usable supported view. Preserve other saved view choices, named saved views and selected context; removal must not leave an invalid dropdown selection or crash old installations.

### Historical discovery needs a replacement contract first

`knownWormholeSystemIds` in `universe-presentation.mjs` and `discoveryPoints` in `universe-map.tsx` currently consume `intel.journey.systems` as remembered discovery membership. Simply dropping `journey` removes wormhole systems previously known through a visit after their live connection expires or disappears.

Replace that dependency with explicit, per-pilot historical discovered-system membership, for example `discoveredSystemIds`, carrying only the identity needed by discovery consumers. Preserve union semantics with current location, selected system, pins, private connection endpoints and usable public reports; public reports expire while private historical discoveries persist. Replay continues to use its own session-scoped discovery set. A distinct-membership projection may still read historical rows, so measure it; deleting aggregate fields alone does not justify claiming all lifetime-history work has vanished. Avoid recomputing membership inside every route leg or every map projection.

### Minimal future recording boundary

The current producer in `server/universe-history.mjs` inserts every changed location into `visits`, then publishes `location.changed`; it also publishes `ship.changed`. It checks `module:pilot`, independently of `module:universe` and the obsolete `module:journey` setting. Its asynchronous name lookup occurs after observation time and sovereignty capture, but before the insert/event publication.

Runtime `visits` consumers are limited to lifetime Universe/Journey projections, the legacy adapter/export, and session queries (combat/replay use those queries indirectly). Goals have no visits-based source. Maps/source tracking consumes accepted location snapshots and owns its own baselines, observations and passages; it does not read this ledger.

A practical target is therefore: discovery remembers only system identity outside sessions; new timestamped movement is recorded for active sessions; session start captures its current fresh location; old stored rows remain available to old sessions and compatibility/export. Resolve active-session ownership at the observation boundary, before asynchronous enrichment, so a response crossing session end/start is not assigned to the wrong session. Unknown/stale start location must remain an honest gap. The legacy preceding-visit fallback applies only when `start.capturedAt` is absent; preserve old rows needed by that fallback rather than inventing a start for new sessions.

Session ownership also needs its own initial-location baseline. If a session starts with a stale/missing location and the next fresh observation has the same system ID as the pre-session snapshot, the current global `id === previous.solar_system_id` early return would skip it. Record that first eligible session observation at its actual time, leaving the preceding gap honest. Conversely, a fresh captured start must not produce a duplicate initial segment. Test this across Pilot disable/re-enable and restart as well as ordinary movement.

The adopted activity policy preserves existing Overview recent activity, `/timeline`, dashboard changes and OBS location/ship notifications under the central activity contract. `core.publish` persists `location.changed` in `events` before broadcasting it, so semantic activity events can still contain timestamped movement outside Sessions. This is an explicitly retained general activity feature; the dedicated lifetime visit log and statistics are the retired feature. Do not claim all outside-session movement evidence has stopped, and do not delete established activity/toast behavior just to make that broader claim. The refactor should make this event ownership distinct from session-owned movement rows and minimal discovery identities.

### Retained session meaning

- `server/session-details.mjs`: `sessionRoute` uses the time-bounded ordered ledger, including loops, equal timestamps, clipped starting context and the preceding visit for legacy inferred starts. `allianceSummary` uses this presence to qualify combat and buffered windows. Do not replace the route with a unique-system set.
- `server/history.mjs` and `server/session-replay.mjs`: preserve report counts and route, live versus ended boundaries, event cursors, killmail occurrence-time handling, replay event cap/coverage, missing coordinates and historical sovereignty. Session-scoped system counts and replay progress are not the retired lifetime product feature.
- `sessionReport` currently reads the raw visit window itself and then invokes `sessionDetails`, whose `sessionRoute` reads it again. This is a confirmed responsibility/query duplication to consolidate as part of travel-service extraction, with explicit raw and derived route contracts. The two queries differ at the end boundary (`<=` versus `<`), so sharing must preserve meaning rather than mechanically replace one result with the other.
- `components/kairo/session-replay.tsx`, `session-replay-map.mjs` and `session-replay-sovereignty.mjs`: retain seek/play/pause, repeated-system travel, transitions between K-space and J-space, session-only discovery/trails and historical/live sovereignty distinction.
- `server/index.mjs` data export still includes `visits`, events, sessions and hidden Journey links. Preserve raw data export and existing storage unless a separate explicit migration is reviewed. Removing a view does not itself justify dropping the ledger or its indexes.

### Obsolete paths require a consumer audit

`JourneyLog` in `components/kairo/intelligence.tsx` has no import/call site in the current application search, and `universeTabForSpace` already normalises retired tabs to Atlas. It is a plausible dead UI export to remove. Its sibling `SessionsPage` and shared report/replay components are active. `ActivityTimeline` currently has its only mount inside the unmounted `JourneyLog`; that is different from the retained backend event API, Overview recent activity and active Session timeline. Decide unused-component removal from actual callers, without deleting those retained capabilities.

`/journey`, `/journey/enrich`, `/journey/connections/:id`, `journeyData`, `setJourneyConnection` and `journey_hidden_links` still have explicit routes/tests/export consumers. They must not be called dead merely because `JourneyLog` is unmounted. Removing the expensive `journeyData` call from ordinary Universe state can deliver the intended hot-path separation while a cold legacy endpoint remains temporarily. Decide removal/versioning of that endpoint contract separately, after checking callers; do not bundle data deletion into the lifetime-counter retirement.
