# Whole-Kairo frontend refactoring review

This extends the checkpoint beyond Maps, Atlas and RC16 additions. It covers the dashboard, Overview, pilot operations, Sessions, Goals, Markets, settings, Stream Studio and browser-source renderer. Application source is unchanged. Existing raw traces are reused for request evidence; all other findings below are code review, not newly timed claims. Priorities are relative to the already measured P1 Maps camera/refresh work.

The useful shared boundary is **scoped resource ownership**: one authority for read freshness, request scope and invalidation, with page-specific rendering and polling policies. A whole-application rewrite, a universal interval, or memoizing every component would not address the actual coupling.

## 1. P2: remove the inherited dashboard refresh cascade

**Measured redundancy, also present in v0.7.3.** `raw/frontend-overview-candidate-1.json` records two initial `/state?character=42` requests, 14 ms apart, plus two `/timeline?limit=5` and two `/goals` requests, all before 62 ms. The equivalent stable trace shows the same duplicated work. In the unchanged 35-second idle window, both versions request `/state`, then `/timeline`, then `/goals` at the 30-second poll. RC16 transfers 4,547 bytes for this three-request window in the minimal fixture. Existing local idle task-time ranges overlap; this is established unnecessary work, not proof of a large idle regression.

The startup path explicitly calls `refresh()` at `dashboard.tsx:74`, while the `[character, !!boot]` effect does so again at lines 104–105. Each accepted refresh replaces the sessions array at lines 60–61. `operations.tsx:22–25` depends on that array identity and reloads both Overview resources even when sessions are unchanged. `ActivityTimeline` has the same identity dependency at `activity-timeline.tsx:29`; `SessionsPage` reloads its archive at `intelligence.tsx:70`; Studio preview depends on it at `studio.tsx:22`. A generic `changed` event is debounced at `dashboard.tsx:148`, but ignores its character ID even though `server/core.mjs:37,55` supplies one. Events for other pilots can therefore invalidate the selected pilot unnecessarily.

**Refactor:** make initial state loading have one owner; retain stable resource identity/revision when contents did not change; map meaningful events to affected pilot/resource keys. Coalesce simultaneous reads and permit one pending follow-up when changes arrive during an in-flight read. Keep the fallback recovery poll, but avoid turning unchanged sessions into an application-wide freshness signal. Cross-reference `followup-whole-app-backend.md`: `/goals` is not a free read—it repeats source evaluation per goal—so frontend request amplification compounds backend work as real goals and snapshots grow.

**Gates:** one initial state read; unchanged fallback poll does not refetch activity/goals/archive; rapid current-pilot changes still converge to the latest data; other-pilot events do not invalidate the active pilot; global events still do. Manual goal edits and automatic wallet/skill/asset/combat progress must continue updating Overview. Replacing `sessions` with only a session revision without a complete goal invalidation contract would create stale goals.

## 2. P2, with a correctness prerequisite: standardize scoped reads and publication

**Code-only lifecycle finding.** `model.ts:91–92` exposes a minimal fetch/JSON helper with no abort signal, resource key or request generation. Individual components recreate different protections: Dashboard has pilot/sequence guards, Goals has pilot/sequence and separate lookup guards (`goals.tsx:19–23`), Markets has generation and alive guards (`markets.tsx:24–26`), settings datasets have an in-flight lock and epoch (`datasets.tsx:26–40`), and SessionReport has generation, request version, and incremental-page coordination (`session-report.tsx:62–93`). This is duplicated ownership logic, not a reason to remove the guards.

`ExtensionPage` at `dashboard.tsx:229` has no stale-response or unmount guard and does not clear the prior result when module/pilot changes. While the same extension remains mounted, a slow request for pilot A can resolve after pilot B's request and publish A's rows. That code path is a concrete scope hazard; this checkpoint did not run an extension race reproduction. `SessionsPage.load` rejects another pilot but not older requests for the same pilot (`intelligence.tsx:62–70`), so a shared helper should preserve both scope and generation, not only one.

**Refactor:** a small read-resource adapter with explicit key (endpoint/query, pilot where relevant, dataset generation where relevant), freshness revision, generation fence, optional cancellation, and stable published value. Keep mutation functions explicit: aborting a fetch does not undo server-side effects. Markets' books are shared resources; its selected scan character is authorization context, so indiscriminately keying every resource by active pilot would duplicate shared caches and could alter behavior.

**Gates:** slow A then fast B, same-pilot out-of-order reads, unmount during pending read, reconnect/dataset generation change, failed request followed by retry, concurrent consumers deduplicated without cross-pilot sharing. Preserve SessionReport's pagination and user drafts, and dataset restart's revision checks. Do not introduce an unbounded cache or a dependency migration merely to get a helper.

## 3. P2: split subscription scope from page rendering and derivation

**Code-only work amplification.** `context.tsx:4–20` exposes all bootstrap, module snapshots, names, sessions, OPSEC and navigation through one context. `dashboard.tsx:224` creates a new provider value on each dashboard update; SSE snapshots replace `data` and merge `names` at lines 140–144. Consumers that need one module therefore rerender when unrelated snapshots or shell state change. The context `time` value is written but has no consumer in the current Kairo components; it is not an application clock and should not become one accidentally.

These renders repeat real whole-collection transformations. `AssetsPage` (`operations.tsx:48`) rebuilds the complete prices Map, maps every asset, and sums values regardless of which Assets tab is selected. Wallet/Character/Industry pages construct multiple row arrays in their parent JSX (`operations.tsx:46–49`), including arrays for tabs that may not be mounted. Overview repeatedly filters the journal, builds its chart and calculates the 24-hour total (`operations.tsx:33–35`). Merely memoizing the outer provider cannot isolate updates when its `data` object legitimately changes.

**Refactor:** keep stable shell/actions separate from pilot resources; subscribe to the resource revisions each page uses; make derived row models/selectors owned by those revisions. Give expensive inactive tab bodies their own component boundaries so unrelated tabs do not prepare their data. Reuse normalized module data and names through structural sharing; do not deep-stringify all snapshots during every render to determine equality.

The eager page imports at `dashboard.tsx:14–20` also couple Overview delivery to Markets, Studio, reporting and Universe. The original checkpoint measured the overall page JS increase (831,476 to 1,370,976 bytes; gzip 238,885 to 388,505). Route module boundaries can defer work and payload, but no separate saving is attributed to a particular library or page without a bundle comparison. Keep navigation and loading/error states stable and preserve preview/detached surfaces.

**Gates:** unrelated snapshot does not rebuild active table/chart row models; required source or name changes do; switching tabs/pilots preserves intended filters and resets scoped rows; missing/stale/disabled module states still render correctly; route loading failures recover. Do not turn the small isolated EveClock component into a timer that rerenders the full provider.

## 4. P2: reuse status subscriptions and distinguish administrative polling from operational work

**Code-only cadence inventory.** Dashboard polls full state every 30 seconds (`dashboard.tsx:149`). Markets polls `/markets` every four seconds, including when idle or hidden (`markets.tsx:25–26`); its sequence guard prevents stale acceptance but does not prevent overlap if a response takes more than four seconds. OBS settings polls `/obs` every three seconds and consumes only `status` after the first read (`obs-controls.tsx:15`), although that endpoint returns both configuration and status (`server/index.mjs:203`). The core already emits an `obs` SSE event (`server/core.mjs:44`), which the dashboard's single EventSource currently does not consume. Goals reloads goals, notes and source metadata together for every relevant source revision (`goals.tsx:20–23`), even though notes do not change merely because a wallet snapshot did.

**Refactor:** use the existing stream to publish OBS status to its UI; use an initial/reconnect fetch for configuration and recovery. Put bounded read scheduling behind the scoped adapter, with resource-specific policy: faster while a market job is running, slower or event/focus-driven while idle, no overlapping reads, and split Goal notes/source metadata from progress refresh. This reduces several homemade loops without forcing every service into the same cadence.

SessionReport is a useful existing counterexample: its 15-second refresh already avoids overlap, hidden documents, static reports and replacing an expanded event collection (`session-report.tsx:67–75`). Dataset settings already use events and focus with one in-flight read (`datasets.tsx:27–40`). Preserve these policies when extracting a common mechanism.

**Gates:** scan progress/completion/cancel/error still appear promptly; cached market books remain visible; reconnect catches missed status events; user-edited OBS configuration is not overwritten by status updates; disabled OBS remains usable in settings; no stale pilot acceptance. Administrative UI polling changes must not suspend backend OPSEC checks, recording, ESI freshness, OBS protection actions or the separately loaded browser source when a dashboard tab is hidden.

## 5. P2 where collections are large: give list processing and incremental history explicit bounds

**Code-only cost, existing safeguards acknowledged.** `DataTable` limits visible rows to 30 but first filters every input row, constructs searchable text and optionally sorts the full result on every render (`ui.tsx:52–54`). Thus pagination bounds DOM, not query/derivation work. `SessionsPage` appends all loaded archive pages into one rendered list and merges them with nested `.some` scans (`intelligence.tsx:66,98–109`); the endpoint returns pages of 30 (`server/index.mjs:298`). Repeatedly loading old sessions can grow both DOM and merge work. This is not a claim that the initial archive is unbounded.

**Refactor:** cache normalized searchable text and derived ordering by rows revision; use an ID Map/Set for archive merges; choose paged/windowed presentation only for collections that demonstrate large use. Move heavy filtering/sorting to a query endpoint when payload and cardinality justify it, with a stable cursor/order contract. `model.ts:87–88` constructs formatters on each invocation; shared fixed number/date formatters are a small P3 simplification alongside row-model extraction, not a headline performance project.

The timeline already queries and renders five rows (`activity-timeline.tsx:21,34`), has a cursor and a 200 ms search debounce. Session report visits start at 40 rows and kill lists at 30 (`session-report.tsx:48–55`); wallet charts are capped at 80 points and disable animation (`operations.tsx:34,41`). These are useful existing bounds. Do not virtualize five timeline rows or replace a chart library solely because Maps is slow.

**Gates:** same search semantics, null/number/string sort behavior, page clamping after updates, stable row identity, accessible expanded row details, ordered session pages with no duplicates, preserved event cursor tie-breaks, and no loss of loaded history during a refresh. Performance validation should use realistic large assets/journal/archive data before claiming a user-visible saving.

## 6. P3: separate Studio editing, preview projection and clocks

**Code-only bounded work.** Studio sends the entire config to `/stream/preview` after a 200 ms debounce for config or source changes (`studio.tsx:22`). Pointer movement rewrites config per move (`studio.tsx:31,53–54`), restarting the debounce even when only x/y changed and source bindings are unchanged. A one-second clock lives in the full Studio component (`studio.tsx:23–24`), rerendering the editor and rules while only time-dependent widgets need new text. The UI caps additions at 50 elements, so this is bounded and unmeasured, below the proven Maps interaction issue.

**Refactor:** separate geometry/edit draft, binding projection inputs, and time-text subscribers. Reproject only when binding-relevant inputs or their source revision changes; commit drag coordinates at frame cadence and preserve the final pointer position. Keep the editor's preview distinct from persisted live output. The current `live` guards avoid accepting superseded preview responses; carry those into the adapter.

**Gates:** unsaved layouts stay unsaved; latest preview wins; bound values refresh for the correct source pilot; dragging and keyboard positioning preserve grid/clamp behavior; countdown/session clock text advances; save/test actions retain existing scope; live iframe and editing mode remain independent.

## 7. P3: preserve the browser source's existing good ownership while trimming redundant writes

`public/stream/render.js` already reuses widget nodes and changes their order only when needed (lines 26–42), limits remembered toast IDs to 500 and active toasts to three (55–56), closes sound contexts after use (48), and restores a fail-closed UNKNOWN layout on disconnect (66–70). Those are deliberate behavior boundaries to retain.

Its interval scans all configured elements every 250 ms and assigns second-resolution clock/countdown text even when unchanged (71). State events synchronously persist the complete layout then update all widget properties (68,30–36). A code-only opportunity is to update time text only when its displayed value changes, schedule only visible time-dependent widgets, and separate persistent layout changes from volatile state updates. No stream CPU or memory improvement is claimed from this static pass. Avoid throttling protection transitions or leaving an obsolete cover geometry in the recovery layout; browser sources are intentionally kept loaded when inactive in OBS.

## Implementation ordering

Start with a narrow resource/refresh contract and the measured duplicate startup/unchanged-poll behavior. Carry the same scope and disposal gates into Maps invalidation consolidation, without making one giant service own every feature. Then isolate heavy selectors/tab components and high-value status subscriptions. Validate larger Assets/Goals/archive and Studio workloads before assigning them the same performance priority as the measured Maps hotspots. Keep timeline/history/discovery retirement as the separately specified migration; raw session/replay facts and broadcast protection are not cleanup casualties.
