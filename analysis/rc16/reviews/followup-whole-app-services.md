# Whole-application service and network review

Reviewed 2026-09-30 against canonical RC16 `57c8dcc7fbd8fc2b62129498d1819050c78381a1`. Scope includes inherited pre-8.0 implementations, not only the RC1–RC16 diff. This is a read-only source audit: no new network measurements, benchmark runs, or production changes. Existing measured evidence is identified explicitly; all other savings remain hypotheses.

The useful service backbone is already partly present: one ESI transport owner, one public combat client, one Auth owner, and domain-specific collectors. Improve these owners and their accepted-work lifetime before introducing any general scheduler/provider framework. Coordinate lifecycle changes with [architecture.md](architecture.md) A2/A6 and [followup-restart.md](followup-restart.md).

## Scheduling and retry boundaries to retain

**ESI already removes repeated transport work.** Reads canonicalize paths and public-name sets, coalesce by pilot/method/path/body, and return fresh cache entries before acquiring network slots (`esi.mjs:50–82`). Public names additionally coalesce overlapping ID sets in batches of 500 (`217–235`); private structure caches remain pilot-scoped. Keep these mechanisms. A POST to public names is a read-like operation, so a generic “all POSTs are commands” refactor would be incorrect. Sequential pagination preserves aggregate stale/truncation/expiry behavior (`204–215`); increasing concurrency is not an established optimization need.

**HTTP freshness and application polling are separate policies.** Core validates module/scopes/current organization before schedule reuse, reads snapshot metadata before large bodies, and coalesces per-dataset work (`core.mjs:167–215`). `polling.mjs:71–84` combines user cadence with server expiry and queue-completion evidence. Preserve that ordering and the protected-evidence cadence; do not collapse these layers into one TTL. Core's batches of three dataset jobs (`302–308`) include enrichment/publishing and are not a second copy of the ESI four-network-request limiter.

**Provider floors intentionally differ.** Combat's shared public client performs cache lookup before its serial queue, coalesces requests by public key, and applies its own pacing and cooldown (`combat.mjs:59–85`). Session history already reuses it (`session-combat.mjs:89`). Universe feeds have per-source flights, deadline checks before normalization, bounded bodies and retained validators (`universe-feeds.mjs:84–144`). EVE Ref owns a separate archive cooldown/body budget (`market-history.mjs:16–20`). Similar Retry-After parsing is a possible tiny pure helper; provider floors, cache meaning and replay rules should remain explicit. No evidence supports merging these into one retry state machine.

**Market job pacing needs a targeted experiment before change.** `markets.mjs:32` waits before calling ESI even when the underlying read cache will hit, unlike Combat's cache-first queue. Repeated cached order-book scans may therefore wait unnecessarily. A cached-history projection already checks its own expiry (`markets.mjs:82`). If a controlled repeated-scan fixture establishes material avoidable delay, apply market spacing only to actual transport through the ESI owner; preserve cache coalescing, true-miss courtesy limits, priority fairness, and cancellation. Do not duplicate ESI cache-key logic inside Markets or remove throttling wholesale. Staged order-book promotion, page/order caps and keeping the previous book on failure (`48–80`) should remain.

## Accepted-work ownership and startup

All located production `combat.ingest()` callers await it: Core killmail enrichment (`core.mjs:148–150`), Combat collection (`combat.mjs:98`), and Session live/history (`session-combat.mjs:62,104,119`). Ingest itself is not in Combat's pending map. Core currently closes Combat before draining dataset tasks (`core.mjs:369–370`); an accepted dataset can resume after the service is marked closed and skip remaining ingestion. This is an ordering input to the architecture lifecycle work, not a separate new lifecycle framework.

The dependency direction is Session → Combat → ESI/Auth, and Imports refresh → Core dataset work → ESI/Auth. No reverse await cycle was found in these paths. Preserve downstream availability while upstream accepted work drains. HTTP handlers await market add/discover/enrich, import operations, and Auth authorization/callback/disconnect (`index.mjs:141–163,183–187,459`); HTTP drain owns those calls (`551–557`). ESI/auth have no explicit close API, so any new quiesce/abort hooks must be coordinated with this ownership order. A generic early abort could discard accepted observations or change a command's uncertainty outcome.

Startup already keeps the supervisor separate from application imports (`start.mjs:1–6`) and constructs one store/vault/Auth/ESI/Core chain (`index.mjs:33–34`). The updater's bounded worker, immutable generation, conditional checks and replacement process are covered by measured [updater.md](updater.md) and the integrated restart follow-up. No updater rewrite is recommended. Windows key unprotection occurs when the vault opens, while token encrypt/decrypt is in-process AES-GCM (`vault.mjs:17–27`); there is no per-request PowerShell launch to optimize.

## Scope and disposition

Reviewed: ESI reads/commands/names/pagination; Core dataset scheduling; polling; Auth and vault; market scan/import/history clients; Combat REST and session/live consumers; Universe public feed client; startup/supervisor/updater ownership. Existing market-history projection batches yield between atomic groups of 100 (`market-history.mjs:43–47`); retain this inherited optimization. Synchronous archive ingestion is visible at `34`, but this audit supplies no new event-loop measurements and does not assign a new regression to it.

Proceed first with the measured live-session cadence fix and coordinated lifecycle work, plus narrow ESI policy consolidation if its semantic tests remain explicit. Cold Auth flight coalescing and worker-exit completion are bounded follow-on changes with clear deterministic gates. Roster caching, market cache-hit pacing and shared R2Z2 transport require workload evidence before expanding the current pass. This audit does not certify every application module or external provider behavior; the complementary whole-app reviews and source tests remain necessary.
