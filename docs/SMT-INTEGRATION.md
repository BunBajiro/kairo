# SMT features in Kairo Universe

This matrix compares the reviewed SMT source at `6b3b4c6a213a349549ef737c89584fc3f048033b` with the pending Kairo 0.8.0-rc.7 implementation. It describes actual workflows and their limits, rather than claiming identical applications. The original inventory, [SMT-WORKFLOW-INVENTORY.md](SMT-WORKFLOW-INVENTORY.md), records the baseline before this integration; its Kairo gap list is not the current release status. Source contracts and attribution are documented in [SMT-SOURCE-AUDIT.md](SMT-SOURCE-AUDIT.md) and [THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md).

“Parity” means the core user task is supported. “Parity + Kairo” means that task is supported with an additional Kairo capability or stronger data handling; the evidence column identifies that addition. “Adapted” means a different interface or platform capability serves the same purpose. None of these labels claims every SMT menu option, identical presentation or data coverage. Unsupported native workflows and other differences are listed below.

## Adaptations and remaining differences

- Kairo keeps a responsive map and one operations dock instead of SMT's eleven independently docked/floating panels. It does not reproduce arbitrary AvalonDock layouts, Windows tray behavior, native taskbar flashing, foreground-EVE-window pilot selection, global hotkeys, click-through windows or simultaneous native overlays per pilot.
- Browser notifications require device permission and browser support. Their lifecycle and click behavior differ from SMT's Windows alarm toasts. Kairo does not copy SMT's DirectSound output/device controls.
- Presentation preferences are deliberately consolidated. SMT's full color property grid, independent font-size/zoom thresholds, every fleet-name cap/mode, overlay opacity and all three editable age-phase timers do not have one-for-one controls. Freshness and reduced-motion behavior are still explicit.
- Signature clipboard compatibility covers the verified English/German/French labels; arbitrary additional client languages are not claimed. Selected deletion currently performs bounded individual record mutations and reports partial failure, rather than an atomic bulk transaction.
- Itineraries use explicit add, move-up/down and remove controls rather than SMT's drag ordering. Infrastructure and connection migration use previewed paste/import and export; Kairo does not automatically watch SMT's preference or infrastructure files. The application does not add SMT's Chinese-language interface or its separate server-status/EVE-clock strip as part of this integration.
- Log-derived location is an explicitly chosen, short-lived observation. It never overrides ESI truth or OPSEC policy. Kairo does not port destructive deletion of old EVE log files, debug editing of physical universe coordinates, or automatic opening of arbitrary links from intel messages.
- Cyno-beacon observations use typed private pins rather than SMT’s global bulk system-list setting. A0 markers use the actual bundled SDE star type names; neither marker family claims current resource availability or a usable cyno.
- EVE-Scout reports and nominal wormhole limits do not establish current mass, hull fit, docking, safety or access. Thera capital restrictions and ship/mass eligibility must be enforced separately from simple geometric connectivity. A manual confirmation is explicitly the user's observation.

## Verification boundary

The matrix is grounded in source inspection, fixture tests and public unauthenticated source checks. Feed fixtures cover stale preservation, bounded requests, expiry, deduplication, resume, shutdown, unknown values and nominal-versus-remaining mass. Routing, operations, import and HTTP tests cover their respective contracts. A named test file is an evidence location, not a claim that every visual preference or native-platform behavior was exercised.

The release handoff must additionally identify the successful exact-head Actions run and packaged-build/browser acceptance result. No private live ESI fleet, structure-search or waypoint command was executed merely to establish feature parity. Current source status and explicit errors are part of the product, not hidden test exceptions.
