## Permission correction evidence

Changes are confined to `server/runtime-lock.mjs`, `server/store.mjs` and `tests/kairo/store-permissions.test.mjs`.

The first three real-filesystem regressions **failed before correction (0/3)** with the relevant actual modes: new launcher root `0755` instead of `0700`, new WAL `0644` instead of `0600`, and crash-retained WAL still `0644` after reopening. They **passed after correction (3/3)**. The retained-crash case commits an actual record into WAL, leaves SQLite unclosed in an isolated child, repairs file modes, verifies the record and `PRAGMA quick_check`, then repeats startup. It also proves an existing `0755` configured directory and its parent are not modified.

Independent review requested two additional permission-failure controls. Injected `EPERM` from database `fchmodSync` and sidecar `chmodSync` must propagate the original error without starting SQLite mutation; the database bytes remain unchanged and subsequent recovery retains the record. The captured descriptor is closed after the `fchmodSync` failure. All **five permission tests pass**. Umask and injected filesystem methods are confined to child processes; ordinary paths restore the umask in `finally`, while the deliberate abrupt-exit fixture terminates only its own process.

The correction adds a fixed number of synchronous file operations during startup: one database descriptor open/chmod/close, two sidecar chmod attempts, and one explicit new-root mkdir. It adds no timers, provider requests, SQL scans, recurring work or directory traversal. The previous post-migration database chmod is removed. Existing accepted-work and dataset lifecycle ordering is unchanged.

## Production data policy proposed for release approval

The 0.8.0 stable baseline should make preservation of durable user data a requirement for subsequent ordinary upgrades. Future changes must distinguish durable user records from explicitly replaceable provider caches, derived indexes and expiring operational data. A destructive change to durable user work requires an explicit product decision and reviewable migration/recovery plan; the historical alpha permission is insufficient.

The supported current recovery procedure is manual: stop every Kairo process, copy the complete data directory and retain its matching package/source identity. Restore the complete checkpoint on the same machine/account, preserve the displaced directory, and verify records before discarding it. There is no automatic pre-upgrade backup or whole-history importer. The browser's local/session display preferences are outside this checkpoint. Windows foreign-account vault recovery is not established and may prevent startup.

Forward migrations must be independently tested from their relevant prior schemas, including failure rollback/retry and repeated startup. Earlier completed migration steps can remain committed when a later step fails; retry with the corrected candidate or restore the full pre-upgrade checkpoint. No blanket atomicity across every service's entire startup is promised. Older executables must not be used against a database already changed by a newer version: rollback means restoring the matching pre-upgrade checkpoint and package, not launching an old binary over newer data.

**Bun's remaining release decision:** confirm that manual complete-directory backup, same-account restoration and no supported in-place downgrade are acceptable for the first stable release, and state the intended supported prior-version upgrade set. Current evidence includes a minimal v0.1 fixture, reconstructed pre-v0.7.3 cache migration, pre-session-travel schema and same-version complete recovery; it does not justify an unrestricted promise covering every historical alpha database. This does not authorize changing the version, merging or publishing.
