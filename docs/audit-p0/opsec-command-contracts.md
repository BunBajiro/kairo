## Selected input, commit and acknowledgment contract

These decisions deliberately tighten the current partial-flat/defaulting and silent list-discard behavior. Existing historical assertions remain evidence of the old protocol; new requirement acceptance must demonstrate the selected behavior. They do not require legacy compatibility under the approved [fresh-data policy](../PERSISTENCE.md#production-baseline-and-version-compatibility).

| Intent | Validation and authoritative ownership |
| --- | --- |
| Manual | One strict boolean plus shared command metadata; CAS only the manual entity. Preserve the policy from the atomic commit boundary. Do not reject a valid Force On/Off because the preserved policy's selected pilot disconnected or needs access repair. Force Off does not itself authorize release: current evidence/policy still decides protection. |
| Policy | Complete four-field policy, strict boolean, nonnegative safe-integer `characterId`; `0` means the current first connected pilot. Validate an explicitly selected nonzero pilot against current roster ownership immediately before commit. Arrays accept positive safe-integer IDs and explicit lossless decimal-positive ID strings only; stable deduplication is canonicalization. Reject malformed, unsafe, nonpositive, overlapping or over-cap input rather than silently filtering/truncating intent. CAS only the policy entity; preserve authoritative manual. |
| Flat/full | Retain a complete flat form with all five fields: manual plus the four policy fields. Validate all fields and **CAS both entities atomically**. Missing/unknown fields and mixed selector forms reject before mutation. A request touching both cannot partly save one entity or use a stale revision for the other. |
| Raw editor input | Validate comma-separated input before accepting its snapshot. Blank separators/whitespace may normalize; malformed tokens retain the draft and identify the invalid input. Return the canonical accepted policy; never claim discarded text was saved. P0-04 settles finite raw bytes/entries and canonical cardinality limits before implementation; current 100-entry truncation is an observation, not an approved budget. |

Commit touched preference fields, their new opaque revisions and the latest bound receipt tuple in one SQLite transaction. The tuple binds entity, storage lineage, command token, base/result revision and immutable validated intent as specified in P0-02A. Every successful new intent advances the touched revision even for equal values. A repeated current token conflicts/read-backs without another mutation. The receipt contains safe canonical values and touched-entity metadata, not provider payloads or an unbounded command history. A flat result identifies both touched entities; later replacement can leave only partial attribution.

Capture the exact canonical commit result at that transaction, then return it separately from current projection/effect status. Never acknowledge a later request's policy or current protection as the earlier command's result. A postcommit classifier, binding, event, SSE or OBS error cannot turn the local save into a rejection or authorize another PUT. A failed transaction leaves preferences/revisions/receipts unchanged and initiates no new command-derived effect.

## Protection and output fence

Core owns the protection authority; Stream and OBS consume that authority through their existing output owners. An authority identity is distinct from durable preference revisions, the classifier's category and an OBS effect-operation identity. Relevant pilot/connection/access/module/evidence or policy changes invalidate the old ownership assumptions, including cases where the category stays equal. Fresh equivalent evidence may revalidate an existing still-eligible operation; it must not automatically cancel/recreate healthy requests or re-run already-applied identical OBS setters. A formerly unknown dispatched setter still needs the separate ordering/completion proof.

1. Immediately after a successful local commit, with **no await or fallible publication between**, invalidate the old authority through minimal synchronous in-memory operations. A changed manual/policy intent cannot leave an old release/binding generation authorized merely because the category is unchanged. Auth/module commits use the same fence under their own contracts. This is not an extra provider fetch or a promise that an external OBS request can be recalled.
2. Install or retain a conservative covered state until the current authority can be classified. Manual On can establish Manual/covered without requiring snapshots, roster access or event storage. For ordinary healthy changes, synchronous classification may directly install the valid current result; do not add visible intermediate flicker, duplicate transitions or broad projection work solely to implement the fence. If projection fails, retain the conservative result instead of an obsolete release.
3. Fence default-pilot bindings when the protected/default pilot changes, and affected explicit bindings when their own authority changes. Public output cannot serve old-owner values while rebuilding. Recompute only affected saved/visible projections using shared inputs; unchanged unaffected bindings retain existing delivery/performance behavior. A policy-only change unrelated to binding ownership does not justify a full-history read or redundant provider request.
4. Revoke obsolete OBS application authority before fallible notification/history/broadcast work. Pending actions recheck the new authority as well as config/collection identity and current evidence validity immediately before release-capable dispatch, including after awaits. Preserve the OBS contract's hide/mute ordering and unknown-after-dispatch rules. A remote getter alone cannot establish that an older setter will not execute later; unresolved unsafe ordering blocks dependent release. Arbitrary configured OBS actions are not a guarantee that real pixels are concealed.
5. Stream installs safe current protection independently of event insertion and ordinary projection serialization. A newly protective update cannot wait behind stale released SSE payloads: use the paired Stream contract's safe immediate delivery or disconnect/fail-closed path, with bounded cleanup. Supply release-capable projection authority and its nonextendable monotonic evidence deadline to that owner. Its bounded client freshness/lease mechanism covers open-but-stalled transport through a passive authority read bound to renderer monotonic request-start time and an exact matching state generation. SSE frames/comments do not renew that lease. Wall-clock anomalies expire/revalidate authority rather than extending the original evidence lifetime. P0-04 settles the timing/cost budgets. No success receipt claims that every renderer received a packet or changed immediately. Client covers, OBS automation and observed real output remain separate evidence.

Full current projection, binding rebuilding, observational history, private/public delivery and OBS scheduling are separately contained follow-ups; failure in one cannot skip the others' required safety ownership. If the process dies between commit and the in-memory fence, startup begins covered and establishes current authority before exposing release-capable output or resuming effects. A failed durable command does not invent a successful new manual preference; ordinary conservative protection remains governed by current committed state and evidence.

## Derived transition history and bounded repair

`opsec.changed` is descriptive derived history, not the durable preference or a gameplay-accounting transaction. Source inspection found no first-party gameplay mutation listener for it: Stream consumes it for optional Stream notifications; [`history.mjs`](../../server/history.mjs) retains event rows and includes them in Session all-event/type counts, while [`session-replay.mjs`](../../server/session-replay.mjs) suppresses OPSEC replay beats. **The events are meaningful retained history**, not disposable or unused data. This disposition must be revisited if a new dependent owner is found.

Keep healthy state/hidden transitions recorded once with their actual observed time, pilot, previous/current state and relevant payload. Reason/metadata-only refreshes and unchanged projections do not fabricate transitions. A temporary internal fence is not itself a new semantic transition if healthy synchronous recomputation establishes the current result before publication. Do not join a pending-event journal to every preference command: safety and durable intent must not depend on successful descriptive event insertion.

Core's transition-record owner may retain **one latest known pending transition** with an opaque unique identity/dedupe key, original observation time, owner and immutable payload. It records through an event insertion boundary separate from bus/publication outcome. A retry/reconciliation of that exact retained identity cannot duplicate the event row; insertion success followed by delivery failure never authorizes another transient toast. Recovery insertion is history repair and must not replay Stream/application toasts or other transient effects. Existing rows and Session count semantics are preserved; do not reconstruct history by changing earlier rows.

No unbounded outbox, per-refresh disk retry loop or permanent per-command transition receipt is selected. P0-04 settles the finite repair attempts, lifetime/bytes and retry scheduling before implementation. If another transition supersedes the pending slot, capacity/deadline expires, storage remains unavailable or the runtime restarts, current authoritative protection still converges. Missing intermediate observations cannot be inferred from the current state. Retain a bounded in-memory known-gap/recording-failure disposition where available; do not promise that a notice survives the same storage/process failure that lost the history. Restart/reconnect initializes current truth without synthesizing unobserved transitions or replaying recovered-state notifications. A later genuinely observed transition is new live work.

## Read-back, queues, cancellation and restart

Add private GET `/api/opsec` as a provider-free, side-effect-free snapshot of both entities' canonical current values, revisions/latest receipt tuples and current protection authority/projection/follow-up disposition. Read it coherently without awaiting providers, triggering refresh or applying OBS. Current effect/history state is explicitly distinct from the immutable local receipt. Public Stream state must not expose private pilot/policy/receipt identifiers.

An unknown HTTP outcome gets one initial bounded metadata read, then deliberate later inspection if unresolved. Matching the full bound tuple proves only that local commit. Old/absent/superseded evidence, a failed read or a profile reset proves neither noncommit nor rollback. Retain the submitted snapshot and newer draft, never automatically resend the PUT, and never use current field equality as receipt proof. Cross-tab writes to the same entity conflict from the same base; independent manual/policy CAS writes merge atomically rather than overwriting each other.

Same-entity accepted successors follow the shared confirmed-predecessor rule and pause on conflict/unknown. Preserve the established same-document queue ordering: an already queued policy must not silently bypass an unresolved earlier manual command. An authoritative precommit rejection or read-back-proven commit can settle that predecessor and release the independently owned policy while preserving whichever manual value is authoritative, not the requested-but-unproved manual value. A generic HTTP error/503 alone does not prove precommit rejection. A genuinely independent fresh policy intent may proceed against its own observed base; this is not a global cross-tab lock caused by one observer's uncertainty. If a future command explicitly declares success of a protective predecessor as a precondition, rejection cannot satisfy that dependency; no extra user workflow is selected here. Flat commands depend on both entities. The browser must bind acknowledgments, catches, busy state and application feedback to the accepted editor/command generation, so navigation or newer text is not overwritten.

The independent rule is symmetric: a fresh manual intent through the existing control, using a freshly observed manual base, may proceed despite unrelated policy uncertainty. Do not leave Force On indefinitely blocked by that uncertainty or add a repair workflow. Preserve already accepted ordered continuations until settled or explicitly superseded; a fresh manual intent supersedes older **unsent** manual successors with an explicit retired outcome so an older opposite intent cannot resume later. Dispatched predecessors cannot be retracted and still face CAS; an intervening commit may cause an honest conflict. This is deliberate new intent, not automatic replay or a global queue reset.

Cancellation before dispatch can discard unsent work. After acceptance, socket loss, navigation or abort does not undo a committed preference or an already dispatched OBS action. Own bounded completion/drain and release observers/resources on every terminal path; preserve unknown outcomes. Runtime restart recovers preferences/receipts in the active storage lineage and initializes protected output before current-state reconciliation. Browser process loss may lose its in-memory token/draft; reopen current truth without claiming a lost command completed/rejected or persisting/replaying its payload. Restart does not certify previous external OBS effects.
