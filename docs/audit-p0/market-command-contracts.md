## Selected local intent and observation rules

Implement strict typed envelopes and exact route/ID validation before acceptance: positive safe integers, declared mode/boolean/strings, one coherent quick delta, valid current scope and finite payload sizes. Do not silently coerce malformed IDs, truncate submitted intent or accept ambiguous remove/add combinations. P0-04 sets the numerical admission/payload/name bounds. Validate the entire defaults batch before writes. Provider results require bounded structural/identity validation before cache or intent publication; unused extension fields need not become stored data.

Use durable storage lineage and server revisions, exact immutable caller tokens/results, one initial **passive local read** after an uncertain reply, and unresolved-successor handling from the shared contract. No automatic mutation resend follows a lost, malformed or generic 5xx response. Accepted work outlives browser socket closure; view cancellation only prevents obsolete UI publication. Recheck runtime activation, dataset-cutover admission, module/access eligibility and target preconditions after body receipt and every preparation await, then at commit/dispatch. A preparation reservation is owned work, not proof that the requested preference committed.

Enabled-only overview cannot supply these bases. The targeted read is bounded and provider-free. A write failure is a definite rejection only when rollback/noncommit is authoritative; an uncertain commit result stays unknown pending passive read. Do not label a storage exception alone as proof that no effect occurred.

### Bounded quick-list merges and first use

This is an explicit extension of per-entity CAS, not last-response-wins or a universal whole-basket replacement API. A live membership is the target entity. An accepted new same-value intent still advances its relevant revision; absence/value equality alone never attributes a command.

1. **Remove a known live item:** compare its caller-observed membership revision at admission and commit. An unrelated item's commit does not make this base stale. Another removal or remove/re-add of the same item conflicts. Recheck the resulting basket is nonempty and no scan has acquired the basket before committing.
2. **Add by unresolved name, or explicitly remove an absent item:** require the caller's basket base to equal current basket revision at admission. Before any asynchronous lookup, reserve a finite preparation bound to runtime epoch, lineage, base and immutable submitted target. Only later basket commits may be merged. Each active preparation retains a bounded set of IDs touched by those later commits, including same-value operations and absent removals. Resolve and bind the exact type ID; aliases resolving to the same ID are the same target.
3. **Commit after preparation:** if the target ID was touched since admission, reject conflict; otherwise apply the delta to the latest basket in one transaction with final scan exclusion, nonempty/80-item limit, revision and receipt checks. This permits a pending add A plus remove B, and independent live-item removals, without losing either intent. An absent remove of A advances the basket revision and touches A, so an older unresolved add A cannot later resurrect it. Same-item opposite intents are ordered by authoritative admission/commit, not click timestamps. Prepare bounded touch bookkeeping before commit and publish it in the same synchronous owner turn before any await; uncertainty invalidates affected preparations, never silently omits a touch because later notification failed.
4. **Finite proof, no tombstone journal:** preparation count, waiters, payload bytes, lifetime and overlap-set size have P0-04 caps. Overflow/expiry invalidates only that pending preparation; it never blocks or rolls back an unrelated valid commit. Restart/lost preparation means conflict/unavailable proof, never inferred disjointness or replay. An unresolved-name/absent request already stale when it first reaches admission conservatively conflicts, even if later resolution might identify an unrelated item. Fresh explicit intent against current state is the recovery. Removed memberships are not reconstructible merely from absence.
5. **Initial built-ins:** before first resolution, the exact built-in catalog is a revisioned virtual initial membership, exposed with stable default-member keys. One shared bounded resolver captures that catalog/dataset/lineage basis, validates a complete one-to-one mapping of the captured names to unique safe IDs from the existing identity response, and atomically materializes metadata and IDs **once** under the still-uninitialized base. No additional per-item verification fanout is selected. This is owned normalization of the same membership, not a user membership change or a user's commit receipt; it must not advance semantic membership, touch all members or reset a later edit. No partial initial basket becomes visible. Failed resolution leaves the virtual state; a late completion uses the already materialized state without overwriting it. Initialization may commit even if a later user delta fails, without attributing it to that delta. Concurrent first-use edits reserve their bases before waiting, then apply their own deltas/receipts with the overlap rules. A first remove A followed by a late independent remove B therefore preserves both; same-target changes conflict.

A Quick/Full scan captures either the materialized basket or that immutable virtual initial basis. Its admitted job owns/joins the same resolver and uses that captured result; it never picks up a later arbitrary basket. Successful scan admission invalidates all older pending basket-edit preparations synchronously before dispatch; failed admission does not. Thus a reserved edit that loses to a scan still conflicts if the scan has already finished when lookup returns. The committed job's exclusion fence prevents new preference edits during its ownership. Item scans bind only their requested type and require no unrelated default-resolution work; History binds its explicit type or admitted local-book scope. Initialization completion is cache/normalization evidence, not scan completion or hidden permission to expand any job's scope. Cancellation of one waiter does not cancel other admitted owners; the resolver itself has finite lifetime and actual drain accounting. Restart/cutover/shutdown destroys preparation/overlap proof; matching a durable revision cannot revive it.

## Selected scan admission, control and outcomes

One runtime Markets owner admits at most one canonical scan task; there is no hidden job queue. HTTP-014 captures caller token, current runtime epoch/lineage, selected hub identity/eligibility, mode/type, comparison intent, basket/local-book scope or fixed derivation rule, selected scan-access pilot/connection/scopes and dataset generation. Capture the optional Jita reference's semantic identity too: its retained hidden row remains usable for comparison, unlike the selected hub which must be enabled. If that reference row is missing, reject admission until an explicit defaults restore; do not silently recreate/follow a hub during the task. Quick captures selected IDs, Full may derive discovered type/history scope from its own validated promoted book, Item stays exact, and History-only never claims a new order-book scan. Input pilot 0 explicitly means no selected pilot; a nonzero scan-access choice on a public station remains captured and eligibility-bound, although its individual public provider requests use 0. Changing dashboard selection never retargets an admitted job. Normal valid token rotation preserves the connection; replacement/disconnect and changed required scopes are distinct eligibility changes.

### Eligibility, recovery and partial commits

Capture and recheck whole-operation ownership around every await, before paced dispatch and before publication/promotion. Any captured nonzero pilot must remain the same connection; private paths additionally require their scopes, and an obsolete response cannot become a current private result. Preserve already accepted healthy observations and same-connection valid token rotation under Auth's contract. Public cache observations remain reusable and the shared book is not deleted by later disconnect. Module disable prevents further provider admission; already dispatched work may settle only under the accepted [module eligibility rules](module-command-contracts.md), with no automatic continuation after the owner has retired. Do not spend extra provider calls to “confirm” every healthy cache hit.

Keep MR-01/02's two-extra-attempt/60-second cumulative recovery-wait envelope across the entire canonical job, including comparison pages. Do not reset it per type, page, joined client, replacement HTTP request or UI retry. Preserve provider cooldowns, validation-before-staging, valid zero-duration/zero-volume exhausted-order handling and terminal permission/page-drift controls. Cancellation/owner checks remain responsive during pacing/recovery. An exhausted/deferred job stops; a later scan is a new explicit command and cannot bypass an outstanding shared cooldown. Auth's uncertain credential POST rules remain a dependency even though market reads themselves do not mutate EVE orders.

## HTTP-015 disposition and browser ownership

**Selected for retirement in implementation:** HTTP-015, the `market-rebuild-v6` migration-only queue/banner and its automatic resume/chaining. Record the removed route's manifest disposition and reject calls to the retired route without effects. Preserve the historical migration/recovery fixtures and receipts; this contract deletes no product code or evidence.

The UI snapshots the exact selected hub/mode/type/compare/access/basket owner and local draft generation for each intent. Render `created` versus `joined` truthfully; cancellation controls capture the displayed job ID. “Continue histories” is a new explicit History command using its selected current access, not a promise to resume the old command. Maintain existing draft edit counters and resource-specific overview errors. A stale action cannot clear a newer field, replace discovered choices in another view, release another request's busy state or announce another job's success. Dirty drafts survive conflicting/unknown results. A committed preference remains successful if overview refresh fails; show that refresh's own error and retry only the read. Background job/card status owns durable progress; application-toast integration and flood limits are P0-03, while Stream toasts remain excluded.
