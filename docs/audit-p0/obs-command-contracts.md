## Observed source boundaries

[`model.ts:api()`](../../components/kairo/model.ts) sends same-origin JSON/CSRF, awaits `fetch` and JSON parsing, rejects malformed JSON/non-2xx, and supplies no retry, AbortSignal, explicit timeout, command identity or expected revision. Well-formed JSON is not a validated acknowledgment envelope. [`index.mjs`](../../server/index.mjs) owns stopping/Host/session/Origin/CSRF admission; `body()` requires JSON content type and limits the raw body to 150,000 bytes before parsing. Accepted handler promises are tracked through shutdown even when the browser socket disappears. An HTTP error alone does not prove no write occurred; explicit domain 409 maps to conflict, other handled errors to 400.

| --- | --- | --- |

`save()` validates/encrypts before its local transaction; synchronous SQLite statements cannot interleave with another JavaScript request inside that commit section. Later asynchronous connection/apply work can overlap another request or protection-state change. [`store.mjs`](../../server/store.mjs) supplies one SQLite connection, WAL and a 3,000 ms busy timeout; those facts are not proof of atomic publication or a command latency budget.

The browser queue survives component remount within one document, not page loss, another tab or runtime restart. [`administrative-refresh.mjs:createOBSControlRefresh()`](../../components/kairo/administrative-refresh.mjs) has separate edit/status generations: dirty/newer drafts survive reads and old save replies; streamed status wins over an older status response. Initial/reconnect reads fetch config+status, ordinary visible refresh fetches status, hidden polling pauses. These are UI ownership fences, not authoritative config versions. Save success can emit an application success toast even though remote errors are separately present in status; the new toast contract is P0-03's responsibility.

## Connection, effect and read-back limits today

[`createOBS()`](../../server/obs.mjs) owns one active socket/connection promise, pending-request map, tracked closing sockets, an apply-running flag and an in-memory generation. Requests use UUIDs; a 6,000 ms default timeout rejects and removes the pending entry. An op7 successful response acknowledges that OBS request; timeout, lost socket or missing response does **not** show whether OBS executed the setter. `cancel()` invalidates generation, rejects pending requests and closes the socket; it cannot undo a remote setter already received. Authentication/version close codes 4009/4010/4011 block automatic reconnect until an explicit configuration/reconnect action. Other closes schedule the default 5,000 ms reconnect. Close waits for tracked sockets/connection up to the configured default 6,000 ms (accepted closeTimeout range 1–15,000 ms).

Apply checks saved collection, sorts hides/mutes before filters, reveals and scene changes, and validates source scene-item ID/name before setting that item. A failed protective action allows remaining protective actions but blocks later reveal/filter/scene actions. Checks between awaits reject obsolete generations; they cannot retract an already-sent request. Successful current application records `appliedState`; caught current failure records error/log. The log retains 30 entries and the UI shows 12. `appliedState` is an earlier application result, not continuous proof that an OBS operator has not subsequently changed output.

Automatic work is part of this contract: connection identification calls `apply()`; collection-change completion calls `apply()`; protection state changes call `apply()`; a generation change during a running apply schedules another pass; and the 10-second interval retries while ready, unapplied, idle, unchanged collection and automation enabled. Existing retries may follow ambiguous timeouts. This is a source-derived uncertainty case requiring controlled tests, **not a confirmed defect or reopening of a historical finding**. The selected reconciliation rule below governs automatic maintenance as well as manual/browser retries.

| Read surface | What it can establish / cannot establish |
| --- | --- |
| GET `/api/obs` | Current saved public config, `passwordSaved` presence and in-memory status. No password, config revision, submitted-command identity or durable effect receipt. Equal values do not prove which command committed; password presence cannot prove which replacement committed. |
| GET `/api/obs/status` | Passive in-memory status read; safe from initiating a connection/effect. It has no command identity or authoritative remote-state proof. |
| GET `/api/obs/targets` → `inventory()` | Reads collection/scenes/inputs and recursively visits groups with a visited set. **If disconnected it calls `connect()`, whose identification may apply automation.** It is not a passive lost-ack reconciliation endpoint. Current scene and item enabled flags describe observations, not prior request history. |
| Source/filter reads inside apply or `/api/obs/filters` | Current source identity/list or filter state. Existing identity/collection guards are distinct from checking whether the desired remote target state was achieved after an ambiguous setter. Full per-action state reconciliation is not implemented here. |

## Selected target semantics

The following contracts follow the coordinator's [shared P0-02A decisions](command-contracts.md), including storage lineage, receipt tuple binding, same-value revision advancement and repeated-current-token rejection. Storage/wire representation remains an implementation choice, subject to those contracts and P0-04 measured limits.

| Boundary | Required behavior |
| --- | --- |
| Config entity and validation | OBS config **and its credential** form one atomic logical entity. Validate the entire request before commit, including explicit types, bounds and unsupported fields. Retain declared normalization only when the acknowledged canonical result makes it visible; do not silently represent discarded intent as fully applied. Compare the entity's expected revision at the authoritative owner; stale input conflicts before config/secret changes, connection cancellation or remote effects. |
| Local commit and exact acknowledgment | Commit config, credential change, new revision and latest command token together. Return that command's canonical public config/revision and local commit result; never reconstruct it from a newer config after an await. Do not return/store/expose plaintext credentials or credential-derived comparison material in the receipt. Successful Save acknowledges the local durable result independently of connection/application; external work has a separate pending/failed/unknown/result status. |
| Bounded local reconciliation | Lost/malformed response or failure after dispatch is potentially unknown. Make **one initial authoritative read** of config revision and bounded latest-command receipt; unresolved results permit deliberate later inspection, not background polling. The matching entity/lineage/token/base/result tuple proves that local commit; an absent/superseded token proves neither noncommit nor rollback. Old state read while a handler may still commit is not rejection. Keep submitted intent/draft and uncertainty when proof is unavailable; no automatic second PUT. CAS conflict requires an explicit renewed intent after reading current state, not silent last-writer overwrite. A receipt is not an unbounded idempotency ledger or an exactly-once promise. |
| Manual reconnect | Explicit request targets an observed saved config revision and current runtime epoch; stale revision conflicts without disrupting the newer connection. It does not save the draft or implicitly enable automation. When disabled/closing, reject as inapplicable before acceptance, with zero effects. When applicable, accept one owned connection attempt, clear the deliberate authentication block as user-requested, and report acceptance separately from identification and any authorized subsequent application. Repeated clicks/another tab join the equivalent active operation by its explicit identity/status rather than repeatedly tearing it down. |
| Manual reapply | Explicit request targets the observed saved revision/current epoch, then the authoritative owner captures current desired protection generation. It does not save a draft or turn on automation. Disabled/disconnected/closed or unarmed automation rejects as inapplicable; collection-changing/closing rejects as busy, before acceptance with zero effects. Equivalent concurrent requests explicitly join the same active operation identity/status with their own observer association; they must not return another operation's result as a new completed application. Superseded desired/config generations terminate obsolete work and permit the latest authorized protection to converge. |
| Remote uncertainty | Separate accepted operation, dispatched action, acknowledged action, failed-before-dispatch, rejected response, and unknown-after-dispatch. OBS request IDs correlate responses on a connection; they do not provide durable deduplication across reconnects. Before retrying an ambiguous setter, obtain safe read-back of the **current target identity and desired state**, with collection/config/desired-generation guards **and evidence that an older in-flight action cannot execute afterward**. If the target already matches and that ordering/completion boundary is established, record present-state convergence without claiming the earlier request executed exactly once. If stable identity and that boundary are proved but current state differs from still-current desired state, the owner may dispatch a fresh bounded convergence setter; earlier historical outcome remains unknown. A getter alone does not establish that boundary. If observation or safe completion ordering is unavailable, retain unknown/blocked state rather than blindly replaying the action/batch or proceeding to a reveal. |
| Automation and ordering | The same uncertainty rule covers the 10-second maintenance pass, reconnect identification, collection changes, state changes and post-run generation follow-up. Preserve authorized convergence and hide/mute-before-reveal priorities. Do not let an unresolved protective action authorize later reveal/filter/scene work. A fresh desired generation may require a different protective action, but it is owned/current-state work, not replay of stale intent. Getters used for reconciliation must be verified against the supported OBS protocol and must not trigger hidden connection/application work. |
| Cancellation and shutdown | Before server admission, abandoned queued UI work is unsent, not saved. After acceptance, browser unload/read cancellation stops that observer, not a committed config or an already dispatched remote effect. Server cancellation fences future obsolete actions and owns bounded cleanup; dispatched actions remain acknowledged/unknown as evidence permits. Shutdown drains or explicitly terminates accepted effect ownership within settled bounds before closing storage. Do not treat a closed HTTP socket or timed-out observer as remote rollback. |
| Cross-tab, drafts and restart | Keep immutable accepted payloads, same-document ordering and newer draft/status guards. A known same-entity continuation may adopt its exact predecessor's confirmed revision; conflict/unknown pauses unresolved successors without silent rebasing onto another tab. Bind responses to command identity plus editor/epoch ownership; newer server revisions update clean editors, dirty drafts remain available for explicit conflict resolution. A runtime restart recovers config/latest local receipt; in-memory remote work is not presumed complete. Recompute current protection state and reconcile remote state before effects resume. Browser process loss may lose in-memory intent: reopen from current authoritative state, without persisting/replaying passwords or pending payloads. Do not replay stale saved operation intent automatically or infer that missing ephemeral status means a setter never ran. |
| Bounded ownership | One connection/apply owner serializes actionable work and publishes separate config-commit/effect status. A lost HTTP acknowledgment for reconnect/reapply never automatically resubmits that operation: make the one initial bounded operation-status read, then leave unknown if retained evidence cannot identify it, with deliberate inspection available. Bound aggregate pending requests, accepted operation records, waiters, retries, queued browser intents and read-back attempts/deadlines; coalesce equivalent/latest authorized work. Retain only the agreed bounded latest receipt/status, not infinite operation history. Concrete caps/backoff/expiry and overflow/cancellation behavior must be settled in P0-04 before implementation. |

Feasibility limits: local config+secret+receipt CAS fits the existing synchronous SQLite owner. Remote OBS effects cannot share that transaction. Present-state read-back can establish convergence only with a valid ordering/completion boundary; it cannot prove absence of earlier transient output or exactly-once execution. A setter accepted/queued in OBS might execute after a getter or after a new desired generation unless the supported protocol/implementation establishes otherwise. Before corresponding implementation, verify ordering/completion assumptions, including across reconnect and old sockets; without sufficient evidence, retain uncertainty and block effects whose safety depends on the old action being finished. Implementation must also identify supported passive getters for source-enabled, mute, filter-enabled and current-scene state, and their collection/identity assumptions; the existing source only demonstrates some of these reads. Automatic connection/application must not be hidden inside those getters. Manual operation identity/result retention and restart epoch handling need a bounded shared envelope, not persistent history of every remote action.

Next implementation units need controlled barriers plus persisted-config/receipt, exact wire request, remote target-state and publication oracles:

1. **OBS-01 — Local validation/commit:** wrong scalar/object/field types, rule normalization/caps/duplicate identity, password unchanged/replaced/cleared, stale revision, same-value revision advancement, fresh-profile lineage and reused-token collision behavior; inject first/second transaction-statement failures and crash before/after commit. No local partial commit or remote effect on rejected input/conflict. Never include secrets in response, diagnostics or export.
2. **OBS-02 — Exact save receipt:** A commits, awaits held connection, B commits, then A responds; A must identify A's exact local result. Test credential replacement where `passwordSaved` alone cannot identify A. Separate local success from connect failure, apply rejection and effect unknown; no false unsaved/applied toast.
3. **OBS-03 — Unknown HTTP acknowledgment:** disconnect before full body, after admission, after commit before response; malformed success; server replacement at each boundary. Matching receipt tuple resolves only local commit; superseded receipt leaves history unknown. Read before delayed commit must not report rejection. Draft preserved, one initial reconciliation read, zero automatic repeated PUT.
4. **OBS-04 — Concurrency:** two tabs with same revision, independent remount queues, queued continuation after confirmed/conflict/unknown predecessor, queued save versus reconnect/reapply, rapid equivalent manual requests, config disable/password/port change while connecting, collection transition and desired-state change while getters/setters wait. Check conflict/no disruption, exact operation identity, owned completion and latest protection; no obsolete reveal.
5. **OBS-05 — Ambiguous remote effects:** fake OBS applies each setter then drops/holds its response; separately reject before execution, and queue execution until **after** a getter/new desired generation/reconnect. Verify passive identity/state reads plus established completion ordering before any resend or dependent reveal, target-already-correct convergence without duplicate setter, unknown when read-back/ordering proof fails, and protective failure/uncertainty blocks reveals. Exercise manual apply **and every automatic apply trigger**, reconnect and late responses from an obsolete socket. Include operator state change and changed/reused scene-item identity controls. A synthetic peer can expose unsafe assumptions but cannot by itself prove real OBS ordering; retain the live/protocol evidence limitation.
6. **OBS-06 — Cancellation/restart:** observer unmount/abort before and after dispatch, closed runtime during handshake/apply, stalled socket close, process restart after local save and after unknown remote setter, browser restart losing in-memory intent. Verify finite cleanup/retained uncertainty and current-state recovery, no payload persistence/replay, stale effect replay or fabricated rollback.
7. **OBS-07 — Resource/performance controls:** withheld replies, large configured rule sets/group inventories, many request callers/tabs, repeated reconnect/error storms, hidden views and long offline periods. Measure aggregate pending/waiter/socket/log memory, request count, event-loop cost, read-back overhead, time to useful protection and cancellation latency against P0-04 budgets.
8. **OBS-08 — Chrome/Firefox acceptance:** saved versus pending/failed/unknown/conflict, dirty/newer drafts, late catch/finally after teardown, same-tab navigation and cross-tab reconnect, keyboard/narrow layouts, optional application feedback ownership. Existing live-OBS exclusion stays explicit.

These are pending requirement acceptance/regression schedules, not confirmed findings. A later defect fix needs a meaningful failing-before/fixed case and independent review. P0-03 settles diagnostics/toast ownership and redaction; P0-04 settles numerical limits and baseline workloads before corresponding implementation. Current 6 s request/close, 5 s reconnect, 10 s retry and 30-entry log constants are **observations, not accepted budgets**; per-request timeouts and a visited-set do not bound aggregate pending requests, total inventory traversal, operation lifetime or retry count.
