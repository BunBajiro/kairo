## Selected admission and command identity

All three commands use exact routes/methods and a strict versioned envelope: fresh token, caller-known runtime epoch/storage lineage, explicit pilot (including0), exact optional map identity/incarnation, and the action's observed command-lane base. Positive pilot manual admission requires its captured current connection after the complete body arrives; replacement A→B→A is not the original connection. No live provider scope is required for manual notes. Recheck current authorization, applicable enablement, map writability/incarnation, catalog basis and base at the atomic commit. Accepted local work is not cancelled by browser departure, but a retired required owner/base before commit rejects without mutation. Delete/ack remain available when collection is disabled. Retained exact receipt inspection remains possible after disconnect; this does not add a disconnected-pilot editing UI.

Select **three fixed command lanes per pilot/scope incarnation**: manual ingest, report delete, alert acknowledgment. Each has a nonreused revision and one latest safe receipt. Stable virtual initial bases bind lineage, pilot, scope incarnation and lane without GET writes. Automatic log intake does not change these user-command bases; unrelated reports/alerts must not starve a submitted command. Commands on one lane from the same base conservatively conflict, even if targeting distinct rows; fresh explicit intent after inspection may proceed, with no hidden rebase. This bounded choice avoids per-click journals and automatic log traffic invalidating all manual writes. P0-04 must bound retained scopes/lanes/bytes together, not only per map.

Allocate a nonreused manual report ID/incarnation on the server only in its final creation transaction, binding its birth to lineage/pilot/scope incarnation/manual-ingest base/fresh token; clients cannot choose or reserve report IDs. Insert-only absence and current lane base are required. Automatic reports likewise receive a server-owned nonreused identity at commit and captured source-delivery association. Every report/alert has an immutable incarnation; no UPSERT resurrects a deleted report/alert. Imported/copied records receive new local incarnations and cannot import receipts, command tokens, live reader authority or notification eligibility. Map lifecycle must atomically retire scope receipts and records and forbid ID/incarnation reuse; detailed map acceptance remains pending.

A new accepted manual disposition, including ignored or semantic duplicate, atomically advances its lane and receipt with no invented report/alert write. A fresh delete/ack similarly records its exact result. Repeating the current token is conflict/readback with zero new commit; changed input cannot reuse it. A superseded token is not replay permission. Receipts contain action/owner/base/result revisions, token, target/result incarnation, outcome and bounded numeric/time metadata, never copied report text, channel/speaker names, raw paths or private-content digests. Record equality or an already-acknowledged state is not attribution of an earlier command.

For manual ingest, allow text≤16,000 code units, optional channel≤100, optional exact RFC3339 observation instant, optional manual kind from report/hostile/clear/question, and at most100 supplied system-ID entries before canonical dedup, each a validated positive safe ID. Bound the combined parser-resolved and explicitly selected set separately under P0-04. Reject wrong types, unknown fields (including claimed source, alert identity, expiry and acknowledgment), malformed dates/normalized invalid calendar dates, nonfinite/overflow values and lossy overflow before mutation. Preserve documented markup removal/trim and system dedup/sort, returning the canonical accepted content; support the full admitted text instead of silently truncating its tail. Parser work beyond the current200-token baseline needs a declared bounded algorithm before implementation; do not claim all16,000 characters were resolved while silently ignoring later tokens. Optional manual time is captured once at admission when omitted, not regenerated on retry/read. Valid dated stale reports remain historical; future tolerance is an explicit bounded policy, retaining the current5-minute allowance as a reviewable source baseline pending P0-04 clock rules.

Local systems resolve against one captured positive atlas generation; ambiguity stays unresolved. No ESI/name fetch, full atlas rebuild or promotion to authoritative location/OPSEC/route access. A map is required for wormhole observations and a tracking-source map remains read-only. Conflicting body/query map selectors reject; omission never falls back from a selected map to the global notebook. Trusted log source/channel/listener comes only from the G2 reader owner, never an HTTP field.

## Record, duplicate, expiry and alert accounting

Select explicit **semantic duplicate** versus **command repetition**. Compare the complete canonical identity tuple after any indexed hash match: pilot/scope incarnation, trusted source, canonical case-normalized channel/text, resolved system set, effective kind/decloak cause and source speaker when present. Do not equate distinct tuples because their hash prefixes collide. Explicit source-time reports deduplicate only at the same canonical source instant. Only otherwise-identical manual submissions with no source instant from either `observed_at` or a parsed pasted timestamp may use the existing5-second receive window; an omitted field alone is insufficient; anchor it to the original report acceptance time and do not extend it on repeats or newer command receipts. A new explicit observation time, kind or speaker is distinct. This selected refinement differs from the current broader OR rule and needs requirement acceptance, not a retroactive defect claim.

Semantic duplication is bounded by retained report evidence; do not promise eternal content dedup after deletion/retention eviction. Command tokens are never reused and automatic source-delivery identity must not rely on this rolling content window. Persist the original alert disposition, acceptance time and bounded config/catalog/location decision identifiers with each report in its creation transaction, including the created alert identity or explicit suppression reason. Do not copy an entire config/location snapshot. This retained evidence, not later alert presence or current configuration, supplies the duplicate outcome even after alert eviction or manual-lane supersession. A duplicate returns the original report/expiry and original alert disposition, labelling any current alert presence separately; no timestamp refresh, new alert, cooldown movement, reinsert or notification. If evidence has been evicted, report unavailable attribution; never invent the earlier outcome. Copy/import are historical records with new identity, not fresh automatic input.

One short local transaction accepts a new report, exact source-delivery accounting where applicable, report/alert retention changes, optional alert, cooldown evidence, required `universe.operational_alert` semantic event and manual lane receipt. Capture one acceptance time/config/catalog/location basis; recheck its relevant authority before commit, with no filesystem/provider await in the transaction. Required failure rolls everything back, including cooldown consumption and receipt. Durable events use stable dedupe identity tied to the alert incarnation; bus/SSE invalidation is deferred until the **actual outer commit**, not nested savepoint release. Do not add semantic events for ignored/duplicate/delete/ack merely to create command receipts.

For a pending automatic line, preserve its original observation/expiry and captured alert-decision basis through recovery. Alert-only settings changes do not replace the G2 reader or discard its decoder/pending bytes. At final commit, require both captured alert eligibility and the unchanged relevant alert-control basis/current eligibility; a changed basis suppresses this line's alert as control-superseded, while its otherwise eligible report may commit. Do not recompute old evidence under newly enabled watches/keywords or a replacement location to manufacture a fresh alert. Unrelated bookmark edits do not suppress it. A committed alert/event remains historical after a later control change; delayed transient delivery rechecks current eligibility and never replays on re-enable. Parser/ignore/lifetime basis changes before an uncommitted line settles require explicit retirement of that prepared line or a separately specified new preparation decision, never silent reinterpretation; this design selects retirement with an honest skipped-coverage disposition, leaving the reader and subsequent lines eligible.

Return separate report and alert dispositions: created/duplicate/ignored; alert created/not applicable/category disabled/expired/no matching evidence/cooldown suppressed/capacity suppressed/control-superseded, with exact IDs where retained. Proximity uses only currently eligible fresh own location, gate hops and captured catalog; watches/keywords/game categories retain their independent meaning. Clear/question never creates danger alerts. No source report is an assertion of safety, live enemy identity or EVE verification. Postcommit publication/reload/serialization failure cannot turn committed records into rejected input or justify reingestion.

Retain current rolling maxima500 reports and250 alerts per scope as source-supported ceilings pending aggregate budgets. Eviction is deterministic and atomic with acceptance; dropping a report also removes dependent alerts, avoiding retained orphan alerts. Ack does not renew report/alert age or reorder history to defeat retention. Commit receipts can outlive a record only in their fixed latest lane slot; no permanent tombstone history. Expired reports remain readable history until explicit deletion/rolling retention; expiry alone never creates fresh alert work. Observation and alert expiry remain fixed from the original source time/captured lifetime; config changes, duplicate/reload/import/restart or a backward clock step cannot revive an already-expired observation. Shared non-extension/clock policy and its cost evidence remain prerequisites.

Operational alert cooldown is **local notification suppression**, distinct from G1/G2 provider embargoes. Persist bounded active cooldown evidence atomically with the created alert/event. The key includes exact pilot/scope incarnation and canonical alert category/system/keyword basis; unrelated owners do not suppress one another. Capture a finite not-before deadline from the accepted alert and applicable config. Repeated input, ack/delete, reconfigure/reconnect or restart cannot shorten an active floor or extend it indefinitely. Expired keys can be reclaimed; never evict an active key merely to admit another alert. If reserved aggregate cooldown/alert-effect capacity is exhausted, preserve the admitted report with an explicit suppressed-capacity alert disposition and no false sent-alert claim. Numeric capacity/deadline, clock/restart handling and fairness require P0-04 approval; current2,000 runtime entries are not a measured budget. This local-only family performs zero provider requests and cannot reset transport cooldowns.

## Exact delete and monotone acknowledgment

Delete captures exact report ID/incarnation and its delete-lane base. Atomically remove that owned report plus **all** linked alerts, advance lane/receipt and return deleted/already-absent with exact target evidence. A current passive read can authorize a fresh absent no-op against the current lane/scope; absence alone never proves an earlier delete committed. Another pilot/map or a replacement incarnation cannot be affected. Absence is not a birth tombstone: an absent-delete cannot reserve or cancel a never-born identity, and an independently admitted create may still commit later under its own server-allocated identity. For a once-born then deleted report, the original create lane is already advanced; replay of that original token/base cannot recreate it, and automatic replay is fenced by its delivery evidence. Concurrent ack and delete serialize to acknowledged-then-deleted or missing-target without orphan/resurrection. Delete does not retract historical semantic events or replay notifications.

Ack captures exact alert ID/incarnation and lane base. First acknowledgment sets one immutable server timestamp; subsequent fresh valid acknowledgment intents return that same timestamp and `already_acknowledged`, advancing only lane receipt metadata. No duplicate semantic event, sound/desktop effect, report mutation, freshness extension or history-order change. This is idempotent **domain state**, not authorization for HTTP retries: repeated current tokens still read back/conflict without writes. An expired retained alert may be acknowledged; a deleted/evicted alert is missing-target with zero domain mutation and cannot be recreated. Ack only changes the private inbox, not real game state or every browser's already-dispatched notification.

## Passive inspection, reader delivery and lifecycle

Select GET `/api/universe/operations?inspect=intel-command` with explicit pilot/scope incarnation and exactly one action lane, optionally the exact target ID/incarnation. Return one coherent local snapshot: lineage/runtime epoch, lane base/latest safe receipt, target present/absent/retired status and current minimal acknowledgment/expiry metadata. Receipt inspection can address a retained captured owner after disconnect. Deleted-scope/evicted-lane evidence is explicitly unavailable, not fabricated proof of noncommit. HTTP-096 continues to own authoritative config/current control bases under G2; ordinary HTTP-095 may include command bases beside display state. Inspection never calls broad `state`, map assembly, filesystem discovery/read, expiry cleanup, parser, name hydration or provider. One initial passive read follows unknown acknowledgment; later deliberate inspection has bounded capacity/deadline. No automatic POST/DELETE replay or indefinite poll. A precommit read, superseded receipt, storage failure, reset lineage or unavailable evidence leaves the old outcome unknown. Restart retains committed receipts; browser loss reads current truth without resubmitting lost drafts.

G2 supplies exact reader/connection/module/config-effect incarnation and filesystem ownership. A delivery also captures file incarnation, byte/line range and stable source-delivery identity. Reserve bounded batch/pending bytes before reading/delivering; decoded complete lines beyond the current per-callback count remain pending for later bounded processing, not silently discarded by slicing. Separate read offset from successfully classified delivery watermark. A batch is not an all-or-nothing import: each line records committed, duplicate, explicitly ignored/malformed, retired or unresolved; preserve the accepted prefix if a later line fails. Automatic location-only Local handling remains a separate G2 location path, not an intel alert or a claim that its accounting was audited here.

Keep at most one bounded unresolved runtime delivery batch per reader, with aggregate runtime limits, until its line outcomes settle. A local transaction failure cannot be swallowed as malformed input; pause further intake for that reader and retain the current bounded bytes/identity for bounded local recovery. Reconcile uncertain commit against exact delivery evidence before any retry, using original observation time/config decision; a repeated delivery never repeats accepted events. Successful per-line delivery evidence is bounded to the pending batch/committed prefix, not an eternal log journal. Recovery cannot resurrect a record explicitly deleted/evicted after that line committed. Budget/deadline exhaustion reports blocked/unresolved coverage and stops intake rather than extending a hidden retry loop or overwriting the pending batch. Independent readers remain eligible under aggregate fairness.

**No durable historical log replay is selected.** Filesystem receipt is not domain acceptance. This runtime pending buffer contains uncommitted observations; restart/re-enable/rotation establishes G2's fresh EOF baseline and does not claim recovery of those unread/uncommitted lines. Committed records/events/receipts survive normally. Explicit reader retirement may discard unaccepted bytes with a truthful coverage gap, never call them committed or replay them under a replacement connection. Any future promise of durable automatic admission before final transaction would require a separate bounded durable staging contract; it is not implied here. Known local commit plus failed callback remains accepted and advances only the exact retained delivery outcome.

Admission closes before shutdown/dataset handoff; fence unsent filesystem reads and obsolete line commits, retain actual I/O/callback occupancy until settlement and drain admitted local transactions before Store close. Browser abort detaches observation only. Config changes unrelated to collection preserve reader offsets/decoder/pending batch; relevant off→on/connection/path/channel changes retire the old reader even if values later match. Do not abort another reader or shared provider consumer. No new cancellation endpoint or provider retry is needed. Uncooperative I/O or unresolved commit is a failed bounded handoff, not proof that resource use ended.
