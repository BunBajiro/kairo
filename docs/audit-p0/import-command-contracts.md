## Selected local settings and plan intent

Require strict typed envelopes, exact hub/plan ownership and finite payload/recipe values before expensive calculation or mutation. Settings saves submit the complete validated policy; reject missing/unknown fields rather than silently reset an omitted field. Recipes contain only declared type ID, strategy, whole-unit quantity, tick-valid price and permitted duration; plan names retain explicit whitespace normalization. Preserve all supported valid planning values and flags, including budget excess and duration-short scenarios. P0-04 must settle numerical byte/admission limits before implementation; existing arithmetic constants are not new performance budgets.

Every mutation captures a fresh immutable command token, storage lineage, owner/base and validated intent. Runtime activation/cutover/shutdown admission is checked after body receipt before domain acceptance; current target/authorization and preparation ownership are rechecked after awaits. Closing admission does not retroactively reject an already accepted local settings/plan save merely because its quote is pending: keep its captured runtime/dataset dependencies alive, let it finish validation/commit within its original budget, then complete drain. Actual access/target retirement, conflicting base or exhausted preparation budget can reject that still-uncommitted save explicitly; shutdown cannot pretend a possibly committed command was cancelled. Use atomic local transactions, never a database transaction spanning an await. The response contains that exact commit's result before follow-up reads/publication; a later state cannot replace it. Shared no-blind-resend, one initial passive reconciliation read, bounded queue, supersession and browser-restart rules apply.

| Entity / action | Selected acceptance, commit and evidence |
| --- | --- |
| Applied settings per hub | One whole-settings CAS entity with latest safe receipt. Validate selected requested roles against current connections; save policy/revision/receipt atomically. Same-value explicit saves advance revision. `characterId:0` means no selected seller; `buyingCharacterId:0` follows the seller. Only absent settings select the initial roster pilot. Quote/refresh resolves and captures the effective role. Settings remain locally editable with Markets disabled or hub hidden, without triggering provider work. |
| Virtual initial settings | Before the first save, expose an authoritative virtual base bound to storage lineage, defaults identity and the effective default seller/buyer/access basis. Do not use a constant revision-zero base while roster order changes the effective seller. Reads do not persist defaults. First save requires both continued row absence and the same virtual basis, then creates the durable entity/receipt atomically. Once saved, normal revision semantics apply; reset changes lineage. |
| Plan identity and membership | Each hub owns a monotonically advancing plan-membership revision and one latest create/delete receipt; each live plan owns a non-reused row revision/latest receipt. Server derives a new opaque plan ID from the caller-known immutable tuple of lineage, hub, observed creation-membership base and fresh nonce, using bounded canonical encoding/hash with validation and no aliasing. The ID is identity, not authorization. The same tuple cannot target another hub/later base; changing that tuple creates a different identity. This prevents a delayed create from resurrecting a subsequently deleted plan without a permanent deleted-ID set. Exact wire encoding is an implementation choice; passive lookup accepts the tuple when the caller has not received the derived ID. |
| Create | Requires that exact absent plan identity and current membership base before preparation and at commit; never UPSERT an existing plan as a create. Atomically check capacity, insert the server quote/row revision/receipt and advance membership/receipt. Simultaneous new creates from the same membership base conservatively conflict, even if capacity remains; no hidden rebase or create retry. Independent existing-plan edits remain independent. |
| Update | Requires the exact hub/plan and caller row revision; recheck existence/base immediately before commit after every quote await. Atomically replace the historical snapshot and advance only that plan's row revision/receipt. Unrelated membership changes do not stale an otherwise valid existing-plan update. A delete followed by late update remains conflict, never recreation. |
| Delete | A live-plan delete CASes its exact row and atomically removes it, advances membership and stores the bounded deletion receipt. Deletion is local and need not depend on currently available trader evidence. An explicit already-absent delete requires an authoritative absent membership base and commits a new membership receipt; absence alone never acknowledges an earlier delete. Concurrent plan update/delete from the same row base cannot both silently win. |

The live row stores its latest exact saved quote, recipe/settings/trader provenance and receipt; the hub slot attributes the latest create/delete even after a row disappears. Receipt tuples bind token, lineage, hub/plan, action, immutable base and result. A repeated current token conflicts/reads; it cannot perform a second mutation or alter its payload. Superseded row/membership evidence, an absent row or equal current values may leave the older outcome unknown. A create receipt can survive a subsequent update: it still proves creation and the plan ID, but its original quote is no longer retained. Tag any returned current snapshot with its own row revision; never present that newer snapshot as the original create's result or replace a newer draft. No old quote history, forever command history, tombstone journal or replay endpoint is selected. Membership receipts exclude large quote bodies and sensitive trader data unnecessary for attribution; plan content remains a private bounded domain record.

Select passive forms on existing reads: **GET `/api/markets/imports?hub=<id>&inspect=settings`** returns only retained/virtual settings basis and safe receipt; **GET `/api/markets/imports/plans?hub=<id>&id=<id>&inspect=command`** returns live/absent target identity, row revision/receipt where present, membership revision/latest receipt and a bounded saved snapshot when requested. Ordinary state also supplies the bases needed for current controls. Validate selectors exactly; do not fall through to broad analysis. These new inspection forms do not call `state`, `analyse`, provider refresh or fee calculation. A reconciliation read may compare the requested immutable command tuple; it must not report old/absent state as noncommit while its handler can still commit. Failure to derive fee UI after a known settings save is a read/projection failure, not a failed save.

## Selected re-quote and offline calculation ownership

**Save approves the recipe and name under the applied settings, with a fresh server quote; it does not freeze the earlier displayed totals.** Preserve this existing behavior and explain it in the existing review description, without an additional confirmation step. Local state/analysis/detail responses expose their applied-settings basis and effective trader/access context. Quote/plan-quote and Save requests carry that caller-observed basis with the immutable recipe; Save also carries name and explicit create/update target/base. Bind accepted work to the applied-settings revision (or virtual basis), effective seller/buyer identities and connection/grant/source-module ownership. Preserve the same immutable recipe/name/plan target throughout. A settings or access-owner change during quoting conflicts or reports unavailable evidence; it must not silently switch traders or apply another tab's assumptions. Ordinary token rotation does not replace a valid connection owner. Ordinary GET analysis/detail observes current state under its own view/operation lifetime; it does not accept a durable save or install a draft.

Books/history and still-authorized snapshot evidence may advance before the final stable quote. Recompute locally within the operation's bounded attempt/time/work budget, then return and persist the **exact resulting saved snapshot**, including its actual quote time/provenance/stale flags. No provider calls are added by analysis, item detail, quote, plan quote or plan save. A changed current market is not permission to modify recipe quantity/price/strategy or substitute another item. Auth renewal uncertainty alone does not revoke already committed valid access/evidence; preserve the Auth contract's distinction between unavailable new credential work and current authorized cached samples. Stored historical quotes remain unchanged until an explicit successful update, regardless of later settings, access, fee rule or dataset changes; historical private reads/deletes do not require reconstructing current trading rates.

Use one consistent validated calculation context for every line and combined packing. Carry internal dependency/access/expiry identity through all promise continuations, including the await between `planQuote` and `savePlan`. Immediately before response or SQL publication, recheck that identity, the captured settings/roles, plan base and required capacity. For a plan commit, the final database dependency/base/capacity check is inside the short local write transaction **before its own writes**, preventing another database connection changing evidence between that check and commit. Do not hold a transaction/lock across calculation or awaits. The plan's own successful write invalidates later memo reuse normally; it is not a self-conflict or permission to repeat the save. A post-quote source change either obtains a fresh coherent quote within the original budget or ends with a typed changed/unavailable result; it never publishes a mixed or expired context. Do not retry against changed settings/roles. Cross-connection SQL invalidation and transaction rollback remain covered. P0-04 must define conservative clock/expiry handling and the calculation deadline; a clock anomaly cannot extend expired evidence into an unqualified current quote.

Preserve one bounded shared computation owner and dependency-specific memo reuse. Compatible waiters may join; unrelated requested hubs remain distinct bounded waiters, not an unlimited promise chain. Every attempt, invalidation retry and join consumes the original operation/cohort's finite lifetime/work budget; new callers cannot renew it indefinitely. Saturation rejects before accepting more work and preserves drafts; exhausted calculation returns a truthful unavailable/changed result with no plan write. Do not return a stale obsolete result as a successful fresh calculation, clear caches broadly, add polling, or silently introduce provider requests to recover. An already valid memo remains usable under its actual access/expiry checks; an unrelated waiter leaving must not cancel it or other eligible consumers. HTTP socket/view retirement suppresses obsolete presentation. Drain owns the entire admitted calculation/re-quote/save continuation and its waiters/retries, not merely a snapshot of one intermediate `flight`; stop admission first, prevent late retry resurrection and settle accepted work before closing dependencies. Bounded drain failure cannot certify a completed handoff.

## Selected trader-refresh admission and partial outcomes

Refresh is a finite provider-read operation with local cache/collector effects, **not a settings commit and not a promise every profile became fresh**. It has no durable command journal. Require fresh command token, caller-known runtime epoch/storage lineage, hub identity/eligibility, expected settings basis and effective selected seller/buyer connection ownership. New refresh requires Markets enabled and the selected hub followed/enabled. Hiding a hub keeps settings/plans/offline cache readable, but retires its refresh eligibility; re-enable does not revive the old operation. Cached hidden Jita remains a valid source/reference under the Markets contract. Local analysis, re-quote and new/update plan save remain permitted for a hidden hub or with Markets disabled when their required source evidence is still authorized; disabling Wallet/Training/Combat can make their owned inputs unavailable. Saved historical inspection/deletion remains available even when those traders or source modules are unavailable. The generic provider-admission fence must not disable these offline paths.

Preserve the awaited HTTP control: POST normally awaits its bounded owner and returns exact created/joined identity plus terminal/partial component outcomes. It does not introduce a background-job UI. If the response wait expires while owned work is still settling, return an exact pending/unresolved disposition when possible; lost transport remains unknown to that observer. Neither HTTP timeout nor a status record releases still-running resources. Passive status inspection supplies later bounded evidence. A newer settings save after admission does **not** retarget or automatically cancel the earlier captured cohort: overlapping valid old/new seller refreshes can finish under their own eligibility, benefiting shared caches and accounting. Retire only obsolete desk presentation; runtime/hub/module/connection retirement still fences affected work. Settings must match at refresh admission, not remain globally unchanged for the entire refresh.
