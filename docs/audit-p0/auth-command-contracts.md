## Observed current flow

[`connections.tsx`](../../components/kairo/connections.tsx) owns public Client ID/scopes and navigates to the server-issued SSO URL. `connect()` joins the same module-level queue as Client ID Save, conditionally persists its selected ID, then POSTs only `{scopes}`. The queue survives remount within one document, not another tab/restart; rejection releases it. **Update access** sends the union of that displayed pilot's scopes, selected scopes and OPSEC scopes, but sends no target pilot or connection revision. The resulting verified SSO identity determines which character is inserted/replaced. Disconnect snapshots the dialog's selected ID into its request, awaits DELETE then bootstrap reload, and emits a success/error toast; it has no authoritative revision/command token or dedicated serialized queue. A reload failure can follow a successful local deletion.

## Selected ownership and commit rules

Use the [shared contract](command-contracts.md) for local receipt tuples, storage lineage, exact results, one initial passive reconciliation read, unresolved queues, cancellation and bounded admission. The Auth-specific choices are:

| Boundary | Selected behavior for implementation |
| --- | --- |
| Application identity | Capture validated Client ID **value and revision**, storage lineage, callback URI, requested scopes and browser-session owner at start admission; recheck after async discovery and before creating/returning the attempt. Pin those values through code exchange and JWT verification. A changed application revision conflicts even if its value later changes back. Client ID changes invalidate obsolete attempts and remain prohibited while connections exist. Store each committed grant's owning application identity; refresh and revoke use that immutable grant identity, never a later global setting. |
| Add versus Update access | **Add** captures the authoritative roster/auth epoch because the pilot is unknown until verification. Explicit connect/disconnect/replacement commits advance that epoch; ordinary token rotation does not. Recheck before exchange when possible and at local grant commit. If epoch changed, reject the stale attempt without replacing current state. An Add result for an already connected pilot conflicts and directs the existing explicit Update access workflow; it does not silently replace that grant. **Update access** captures a specific pilot and expected connection revision; the verified identity must match, and the connection must still match at commit. Other pilots' independent updates need not invalidate this targeted attempt. |
| Bounded connection identity | Explicit connection commits allocate a nonreused revision from the profile's auth epoch/lineage; live rows carry their revision. Disconnect atomically removes its row and advances the roster epoch/latest roster receipt. Do not keep an ever-growing tombstone/attempt journal for every historical pilot. Concurrent generic Add attempts may conservatively conflict after an unrelated explicit roster commit: the user starts a new explicit attempt from the current roster. This is the selected safety/concurrency tradeoff, not a guarantee of concurrent arbitrary Add completion. |
| Callback validation and consumption | Admit only the documented GET callback. Validate exactly one state and a coherent success-code **or** provider-error response; reject duplicate/invalid known fields, while safely ignoring unrecognized response parameters as OAuth requires. Success **and cancellation/error** must validate/consume the matching unexpired session-bound attempt. Consume before any exchange; duplicate callbacks cannot issue a second token POST. Recheck captured app/target preconditions after asynchronous work and at commit. Never log/export raw URL, state, code, PKCE verifier, token or headers. |
| Provider response validation | Fully validate bounded metadata/JWKS/token/JWT schemas, safe-positive character identity, finite times, supported algorithms, issuer/application audiences, scope string entries and required token types before local grant changes. Do not infer grants from requested scopes. Enforce the configured trusted SSO endpoint origin and safe redirect handling before secrets can be forwarded. The exact supported field/type/size policy requires tests and P0-04 bounds; an example code snippet is not a replacement for that validation. |
| Atomic local grant | Finish validation/encryption first. In one local transaction recheck app/roster or targeted connection preconditions; perform required owner-change snapshot/cache purge, grant UPSERT, revision/epoch and safe latest commit receipt. No transaction crosses network awaits. Failed transaction leaves the previous committed fresh-profile state intact. Advance runtime ownership only with committed state, then publish/invalidate and schedule bounded authorized collection as separate follow-up outcomes. Callback read-back/redirect must not call a committed grant “failed to connect” merely because follow-up publication failed. |
| Disconnect commit | Require exact route, valid positive safe pilot ID and expected connection revision; reject stale/absent targets before effects. Atomically remove credentials/snapshots/private cache and advance epoch/latest safe receipt. End local request eligibility at that commit, preserving intended retained domain history. Local acknowledgment is independent of revocation latency/outcome. Snapshot only the old credential/app into the bounded revocation owner; a fresh login must never be removed, marked reauth or locally changed by the old operation. |
| Revocation result | Make at most the one admitted revocation POST for that disconnect. Classify no endpoint/unavailable-before-dispatch, definite failed response, acknowledged revocation semantics, and unknown-after-dispatch separately from local success. Do not treat every HTTP status as success or automatically replay an unknown revoke. Release transient credential material at bounded completion; runtime restart does not recreate/replay the revoke. A fresh login during old revocation remains locally authoritative, but provider-side grant overlap/cascade may still invalidate access: do not claim remote isolation. |
| Publication and scheduling | Invalidate relevant roster/state/goals/protection/bindings using the committed generation; ensure fail-closed protection updates are owned rather than waiting silently behind revocation. Required projection rebuild/collection admission can recover from committed state without repeating login/disconnect. Preserve module/scopes/connection eligibility and provider deadlines. Missing SSE acknowledgment is not missing commit; no extra auth request to repair a view. |

The epoch/revision checks are local concurrency rules, not a claim to order provider grants globally. Two code exchanges may already have occurred before one loses its local commit race. Do not blindly revoke the rejected exchange's grant as cleanup: provider revocation may overlap the accepted grant. Discard uncommitted credentials securely, preserve the known local result, and expose the remaining external uncertainty without claiming a remote rollback. No existing-data migration/compatibility gate is introduced.

## Uncertain provider and browser outcomes

Authorization-code exchange and token refresh are provider mutations. A safe roster GET cannot recover a token response that was never durably captured. These boundaries are required before changing Auth commands:

- **Start/callback:** bind a bounded attempt identity separately from secret OAuth state. On lost start acknowledgment, one session-authorized passive read may recover the same still-unused attempt/URL; it must not create another attempt or navigate as a side effect. Completed local receipts identify only their exact commit. An expired/lost runtime attempt, superseded receipt or read before an active callback commits does not prove provider rejection. Never resend a code. A deliberate new SSO flow is new intent; do not replay browser-persisted codes, verifiers or pending payloads after restart.
- **Refresh dispatch:** preserve per-current-token single flight. After safe preparation and immediately before the first token POST, atomically arm a bounded durable marker bound to the current connection and encrypted-token version. Marker/storage failure prevents dispatch. Crash after arming but before send may conservatively require fresh SSO; it cannot justify guessing that send did not occur. Ordinary observer cancellation does not cancel all eligible refresh consumers.
- **Refresh completion:** valid response plus successful encryption/conditional transaction atomically installs the new token bundle/grants and resolves the marker. Superseded connection rejects the old result without disturbing its replacement. A definite `invalid_grant` marks only its matching connection; never infer it from timeout or malformed JSON. Timeout/lost response, received invalid tokens, failed validation, encryption or persistence leaves the old credential **unusable for automatic refresh replay**, with explicit credential uncertainty/fresh-SSO recovery. If passive metadata/JWKS validation alone failed after a complete token response, bounded in-memory validation retry may reuse that response without a second token POST; expiry/limit/restart ends that option. A validated token whose durable commit failed must not be returned to consumers as installed access.
- **Restart:** an armed/unresolved refresh marker remains blocked until deliberate fresh SSO or a separately verified provider recovery mechanism; do not discard the marker and automatically POST the old token. Safe read-back may establish local committed/current connection state, not provider rotation history. Callback attempt secrets stay ephemeral; successful grant receipts survive normal runtime restart, while unfinished exchange can remain unknown. The browser may lose its pending in-memory intent without either replaying it or fabricating its outcome.
- **Cooldown and failure:** metadata/key reads can retry under finite shared budgets and server cooldowns; no generic retry wrapper wraps token/revoke POSTs. Definite provider failures and before-dispatch failures need distinct policy, with no automatic resend selected for a dispatched uncertain mutation. Preserve the original safe error classification if diagnostics or cleanup also fail.

One current refresh marker per active connection and one bounded latest roster/connection receipt avoid permanent command history. When a connection is removed/replaced, obsolete flights cannot delete the replacement's marker or receipt. Aggregate admission/waiter/byte/time caps still belong to P0-04; durable markers do not themselves bound live promises or token-response buffers. Any new background revocation/validation owner must be included in shutdown drain before dependent storage/vault closes.

## Primary protocol checks and limits

Primary sources were opened on **21 October 2026**; these support the limited external constraints below, not live EVE acceptance. No provider credentials or live authorization were used.

| Source | Constraint used here |
| --- | --- |
| [Current EVE developer SSO guide](https://developers.eveonline.com/docs/services/sso/) — PKCE and JWT sections | PKCE binds verifier/challenge; state must be verified; authorization code is one-use; application/character/granted scopes come from validated token claims. Discovery provides endpoint locations. The old `docs.esi.evetech.net` pages explicitly say they are no longer updated, so this document uses the current guide. |
| [RFC 6749 §§4.1.2, 4.1.3, 6](https://www.rfc-editor.org/rfc/rfc6749.html) | Codes are single-use and bound to client/redirect URI. Refresh responses may replace the refresh token, so loss of a response is not proof the stored token is still safely reusable. Unrecognized authorization-response fields are ignored; duplicates are not accepted as multiple competing values. |
| [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html) | Rotation is one replay-detection mechanism; replay can invalidate the active refresh grant. This motivates conservative uncertain-refresh handling. It does **not** prove EVE currently rotates every request. |
| [RFC 7009 §§2.1–2.2](https://www.rfc-editor.org/rfc/rfc7009.html) | Revocation may affect related tokens/grants. A 200 can also mean the submitted token was already invalid; it does not prove this request uniquely invalidated it. No source here establishes isolation between an old revoke and a later EVE authorization. |

Precise provider error/cooldown behavior, supported token schemas and live SSO grant overlap remain implementation evidence dependencies. Do not assume a token-introspection/read-back facility, request deduplication key or safe POST replay that these sources do not establish. Native Windows/DPAPI, real EVE SSO/roles and extended use remain outside automated acceptance.

7. **AUTH-07 — Revocation overlap:** missing endpoint, before-send failure, non-2xx, acknowledged already-invalid token, server accepts then drops response, delayed revoke racing fresh login, crash/drain.
