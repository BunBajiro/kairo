## Observed current flow

[`connections.tsx`](../../components/kairo/connections.tsx) owns public Client ID/scopes and navigates to the server-issued SSO URL. `connect()` joins the same module-level queue as Client ID Save, conditionally persists its selected ID, then POSTs only `{scopes}`. The queue survives remount within one document, not another tab/restart; rejection releases it. **Update access** sends the union of that displayed pilot's scopes, selected scopes and OPSEC scopes, but sends no target pilot or connection revision. The resulting verified SSO identity determines which character is inserted/replaced. Disconnect snapshots the dialog's selected ID into its request, awaits DELETE then bootstrap reload, and emits a success/error toast; it has no authoritative revision/command token or dedicated serialized queue. A reload failure can follow a successful local deletion.

## Selected ownership and commit rules

Use the [shared contract](command-contracts.md) for local receipt tuples, storage lineage, exact results, one initial passive reconciliation read, unresolved queues, cancellation and bounded admission. The Auth-specific choices are:

| Boundary | Selected behavior for implementation |
| --- | --- |
| Application identity | Capture validated Client ID **value and revision**, storage lineage, callback URI, requested scopes and browser-session owner at start admission; recheck after async discovery and before creating/returning the attempt. Pin those values through code exchange and JWT verification. A changed application revision conflicts even if its value later changes back. Client ID changes invalidate obsolete attempts and remain prohibited while connections exist. Store each committed grant's owning application identity; refresh and revoke use that immutable grant identity, never a later global setting. |
| Add versus Update access | **Add** captures the authoritative roster/auth epoch because the pilot is unknown until verification. Explicit connect/disconnect/replacement commits advance that epoch; ordinary token rotation does not. Recheck before exchange when possible and at local grant commit. If epoch changed, reject the stale attempt without replacing current state. An Add result for an already connected pilot conflicts and directs the existing explicit Update access workflow; it does not silently replace that grant. **Update access** captures a specific pilot and expected connection revision; the verified identity must match, and the connection must still match at commit. Other pilots' independent updates need not invalidate this targeted attempt. |
| Bounded connection identity | Explicit connection commits allocate a nonreused revision from the profile's auth epoch/lineage; live rows carry their revision. Disconnect atomically removes its row and advances the roster epoch/latest roster receipt. Do not keep an ever-growing tombstone/attempt journal for every historical pilot. Concurrent generic Add attempts may conservatively conflict after an unrelated explicit roster commit: the user starts a new explicit attempt from the current roster. This is the selected safety/concurrency tradeoff, not a guarantee of concurrent arbitrary Add completion. |
| Callback validation and consumption | Admit only the documented GET callback. Validate exactly one state and a coherent success-code **or** provider-error response; reject duplicate/invalid known fields, while safely ignoring unrecognized response parameters as OAuth requires. Success **and cancellation/error** must validate/consume the matching unexpired session-bound attempt. Consume before any exchange; duplicate callbacks cannot issue a second token POST. Recheck captured app/target preconditions after asynchronous work and at commit. Never log/export raw URL, state, code, PKCE verifier, token or headers. |
| Provider response validation | Accept bounded JSON objects only. Required metadata endpoints are nonempty HTTPS URLs at the trusted SSO origin, without credentials/fragments; optional revocation, if present, follows the same rule. JWT header requires RS256 and a string key ID resolving to an unambiguous usable RSA key; verify signature before trusting claims. Require supported issuer, string-array audience containing EVE and captured Client ID, required finite numeric expiry and finite numeric not-before when present, safe-positive integer character subject, and array-of-string granted scopes. Enforce expiry later than the current time and not-before validity; P0-04 fixes any permitted clock skew/margin. Optional name/owner must have their declared string/null shape. Token response needs nonempty string access token, case-insensitive Bearer token type, and nonempty refresh token for callback; refresh may omit a new refresh token, preserving the old one only on fully validated success. Ignore unused provider extension fields without persisting them. Reject invalid shapes rather than coercing them. P0-04 chooses byte/count bounds; these type/identity requirements are fixed. |
| Atomic local grant | Finish validation/encryption first. In one local transaction recheck app/roster or targeted connection preconditions; perform required owner-change snapshot/cache purge, grant UPSERT, revision/epoch and safe latest commit receipt. No transaction crosses network awaits. Failed transaction leaves the previous committed fresh-profile state intact. Committed revisions are authoritative; update any runtime mirrors synchronously before yielding, and rebuild them from storage on restart. Then publish/invalidate and schedule bounded authorized collection as separate follow-up outcomes. Callback read-back/redirect must not call a committed grant “failed to connect” merely because follow-up publication failed. |
| Disconnect commit | Require exact route, valid positive safe pilot ID and expected connection revision; reject stale/absent targets before effects. Atomically remove credentials/snapshots/private cache and advance epoch/latest safe receipt. End local request eligibility at that commit, preserving intended retained domain history. Local acknowledgment is independent of revocation latency/outcome. Snapshot only the old credential/app into the bounded revocation owner; a fresh login must never be removed, marked reauth or locally changed by the old operation. |
| Revocation result | Make at most the one admitted revocation POST for that disconnect. Classify no endpoint/unavailable-before-dispatch, definite failed response, acknowledged revocation semantics, and unknown-after-dispatch separately from local success. Do not treat every HTTP status as success or automatically replay an unknown revoke. Release transient credential material at bounded completion; runtime restart does not recreate/replay the revoke. A fresh login during old revocation remains locally authoritative, but provider-side grant overlap/cascade may still invalidate access: do not claim remote isolation. |
| Publication and scheduling | Invalidate relevant roster/state/goals/protection/bindings using the committed generation; ensure fail-closed protection updates are owned rather than waiting silently behind revocation. Required projection rebuild/collection admission can recover from committed state without repeating login/disconnect. Preserve module/scopes/connection eligibility and provider deadlines. Missing SSE acknowledgment is not missing commit; no extra auth request to repair a view. |

The epoch/revision checks are local concurrency rules, not a claim to order provider grants globally. Two code exchanges may already have occurred before one loses its local commit race. Do not blindly revoke the rejected exchange's grant as cleanup: provider revocation may overlap the accepted grant. Release references to uncommitted credentials promptly; do not claim guaranteed memory zeroization in JavaScript. Preserve the known local result and external uncertainty without claiming remote rollback. No existing-data migration/compatibility gate is introduced.

### Attempt and receipt lifecycle

Auth owns one aggregate bounded attempt registry, with a second per-session admission cap; same-cookie tabs share that session cap. Reserve a slot **before** discovery. Each accepted start carries a fresh caller-generated command token, immutable payload, runtime epoch and initiating session; state/verifier and the approved URL are private ephemeral fields. A duplicate current token conflicts/read-backs instead of allocating another attempt. Capacity rejection precedes acceptance; accepted attempts are not silently replaced to admit newer ones. Different attempts may coexist within the caps; an explicit new login does not erase an older accepted attempt, although its later commit can invalidate that older attempt's precondition.

The private bootstrap exposes the current runtime epoch before start, so the caller already knows the token/epoch pair if the start response is lost. The private start envelope has a strict Add/Update mode, command token, expected runtime epoch, expected application revision and catalog-scopes array; reject a stale runtime epoch before admission. Add supplies the expected roster epoch, Update a positive-safe pilot ID and expected connection revision. Reject unknown private-command fields and conflicting/missing mode fields. Empty requested scopes remain valid selection; a callback without the refresh token required for a lasting Kairo connection fails locally without inventing a grant. Disconnect supplies command token and expected connection revision for its exact path target. Serialization names are implementation choices, not permission to omit those preconditions.

| Attempt state | Transition, retained data and authoritative read |
| --- | --- |
| Preparing → ready | Validate/capture app/roster or target, await shared discovery, then recheck before allocating state/PKCE and publishing URL. Retain the exact admitted tuple and expiry. A failed preparation terminates without token exchange. |
| Ready → exchanging | Valid matching callback atomically consumes the state and claims the attempt before any await. A provider error terminates as cancelled/rejected with no exchange. Success uses one code POST; duplicate/expired/foreign callbacks never take a second claim. Expiry applies before claim; claimed work has a separately bounded completion deadline. |
| Exchanging → terminal | Commit the matching grant, or finish rejected/superseded/unknown as evidence permits. The operation owner's deadline or runtime shutdown can revoke subsequent local commit authority; browser navigation/socket closure/observer cancellation alone cannot cancel accepted work. No additional domain-cancel command is selected here. Discard an obsolete late provider response without claiming it never issued credentials. Remove code/verifier/URL and token-response references at terminal completion. |
| Terminal → evicted | Retain safe status/receipt metadata and the private consumed-state lookup association described below, separately from safe DTOs, for a finite retention period within count/byte limits; then evict both. A periodic expiry sweep runs independently of new starts; ready/preparing expiry releases their secrets and slots. Active work cannot be evicted while its resources are still live; cancel/drain under its own bound, reject excess new admissions. Shutdown invalidates ready attempts and drains claimed operations; no attempt secrets survive restart. |

One private passive read, keyed by the caller's start token/epoch and authenticated initiating session, returns stage, captured public preconditions, expiry and safe outcome; it never creates an attempt, refreshes a token or navigates. Only that session may recover the same **still-ready** redirect URL, which necessarily contains OAuth state. Never put that URL/state in general receipts, diagnostics, export, Stream or another session's response. A lost start response can be inspected using its already caller-generated token; never-admitted, unavailable or evicted attribution remains unknown. No polling loop is selected: one initial reconciliation read, then deliberate inspection.

Ordinary SSO navigation destroys the initiating page's JS memory. The callback therefore redirects to the private dashboard with only the nonsecret command token and runtime epoch as a continuation reference, never OAuth state/code/verifier. That reference does not authorize a read: the initiating authenticated session must still match. The new page uses it for its one initial passive result read, then removes it from the visible URL without persisting pending OAuth payloads. Keep a private consumed-state→attempt association within the same bounded registry through terminal retention so a duplicate callback from that session can redirect to the same status reference without another exchange or reclassification. A lost redirect does not repeat the mutation; the browser may revisit the original callback, which performs this lookup only. Unknown/evicted/wrong-epoch association gives unavailable attribution, not rejection. Runtime loss removes this mapping; an authorized current roster read may independently prove a surviving exact durable receipt, but neither callback replay nor automatic new login is allowed.

Persist one latest roster commit receipt slot for the whole profile and one latest explicit connection receipt on each **live** character row. A slot is not the logical command entity: Add's tuple binds its expected/result roster epoch and created pilot; Update/Disconnect bind pilot, expected/result connection revision. Disconnect allocates its result revision in the receipt even though its row is removed. The latest roster slot copies that exact command tuple plus roster before/after epochs. Receipts contain the shared owner/entity/lineage/token/base/result tuple, operation kind and safe result only; no OAuth state, secret or private-content digest. Grant commit updates both applicable slots; disconnect leaves its exact local result only in the latest roster slot. A later roster commit can supersede it, making older attribution unknown. Token refresh uses its separate credential marker/version and never overwrites an explicit Connect receipt. This bounds receipts by the live roster plus one; no deleted-pilot tombstones. GET bootstrap/roster may expose current revisions and safe receipts without invoking `access()`; attempt secrets remain session-scoped. Wire endpoint names are implementation choices, and new read routes must be registered in the coverage manifest.

## Uncertain provider and browser outcomes

Authorization-code exchange and token refresh are provider mutations. A safe roster GET cannot recover a token response that was never durably captured. Never resend a consumed code or automatically restart its login. The selected refresh state machine uses one durable marker per live connection, bound to connection revision, opaque credential version and a fresh operation token; it contains no copied token or token-derived digest.

| Refresh boundary | Required disposition |
| --- | --- |
| Preparation, no POST invoked | Recheck connection/credential eligibility, prepare metadata and reserve bounded flight/waiters. Before-dispatch read failure may recover under shared cooldown/read budgets; no marker means no armed send. Atomically arm the marker only after preparation. Dispatch is forbidden until marker commit is positively known. If marker commit is uncertain, inspect matching local state without sending; storage uncertainty blocks the owner. |
| Armed, definitely not dispatched in this process | A current owner that knows it never invoked transport may clear **only its matching marker** by a confirmed conditional transaction; then future eligible callers can prepare again. Failed/uncertain clearing keeps it blocked. Crash loses the no-send proof: restart treats any armed marker as unknown, even if the crash actually preceded send. |
| Dispatched, active | One POST owns the credential version; same-version callers share that flight within waiter bounds. Observers can detach without cancelling another eligible consumer. While live refresh is healthy/pending, already dispatched same-connection ESI work remains eligible; ordinary successful rotation does not change connection intent revision. |
| Complete response / bounded passive verification | Keep the same active flight/armed marker while validating identity/application/scopes. A transient metadata/JWKS failure may retry only those reads, retaining the response in bounded memory until the verification deadline; no additional token POST. This remains pending verification, not terminal blocked state. Invalid claims or exhausted verification bounds terminate as blocked below. |
| Complete validated response | Encrypt, then transactionally replace the matching credential **and actual verified granted scopes** and resolve marker, advancing credential version without changing explicit connection intent revision. Never retain obsolete advertised scopes or infer grants from requested scopes. Current granted scopes must fence ESI dispatch/publication; healthy same-scope rotation keeps accepted work eligible. A failed CAS caused by replacement/disconnect terminates the obsolete flight without touching the new connection. If the new credential transaction is uncertain, one authoritative marker/version read within the active flight may prove its exact commit. A confirmed commit remains success despite subsequent notification failure; it does not require fresh SSO. Never return an uncommitted token as installed access. |
| Definite OAuth rejection | A validated expected token-endpoint error response can establish rejection, not success. `invalid_grant` sets reauthorization and blocks access for only its matching connection. Other recognized rejection codes block renewal pending correction/fresh SSO; **this unit selects no automatic token POST retry**, even for them. Persist this state conditionally; if persistence fails, retain the armed marker plus immediate in-process disposition. A bare non-2xx, 3xx, malformed/error body or intermediary response is insufficient proof of no issuance and follows unknown handling. |
| Terminal unknown or unusable response | Lost/truncated response, invalid token/claims, exhausted passive verification, encryption/persistence failure or unavailable commit evidence blocks the matching **refresh capability** as unknown. Never POST that refresh token again or deliver the received-but-uncommitted token. Discard transient token response material. No automatic validation/POST retry restores terminal renewal capability. The residual armed marker safely blocks renewal even when writing status failed; previously committed access follows the separate rule below. |
| Restart / explicit recovery | Armed/blocked state forbids old-refresh-token replay after restart; only already committed verified access may remain usable under the rule below. Fresh explicit Update access replaces that connection/marker atomically; Disconnect deletes them. A separately reviewed provider recovery mechanism would need its own evidence before changing this renewal rule. Safe reads expose local state only, not provider rotation history. |

**Access versus renewal:** rotation uncertainty alone does not establish that the previously committed access token was revoked. Auth may continue supplying that already verified token while it remains unexpired and belongs to the same application, connection and granted scopes. It must check the renewal marker before any fast path that could refresh, and never substitute the uncommitted response token. Show renewal unavailable/unknown separately from current access. At expiry, explicit current-token 401, known `invalid_grant`, verified ownership mismatch or explicit disconnect/replacement, stop that token's use; an uncertain refresh cannot revive it. A force-refresh call after 401 returns the blocked-renewal outcome rather than falling back to the rejected token. Attribute a 401 to the actually delivered credential version so a late old-token rejection cannot poison a newer committed token/login.

Keep ordinary ESI connection/scope/freshness/cooldown checks around dispatch and publication. Valid in-flight observations may publish when those checks still hold; ambiguous refresh alone does not invalidate every accepted read or delete valid samples. Known loss of grant/ownership must fence subsequent dispatch and late publication, with an immediate in-process eligibility block even if persisting that status fails. A persisted rejection preserves access denial across restart; a failed rejection/status write cannot. After such a crash the residual armed marker proves only renewal blocking: previously committed verified access may again be eligible until normal expiry/current-token denial. Do not claim durable knowledge that was never committed. Last-good data/history remain inspectable with accurate freshness/access status, never empty success. This is a deliberate availability choice, not a promise that EVE retains old access after rotation. Healthy successful rotation still preserves connection intent revision and accepted collection work.

Honor any applicable validated provider cooldown before later metadata/key reads or new explicit flows; no diagnostic or status read generates provider traffic. The baseline design permits one admitted code/refresh/revoke POST and bounded passive verification; no numerical wait, retry, cache or capacity value is finalized here. Code-exchange, refresh and revocation transports follow **no redirects** after sending credentials, including 307/308: classify the response as unconfirmed failure/unknown, never resend credentials at its Location. Endpoint reads likewise must not escape the trusted origin through redirects. All new background Auth work joins runtime drain before Store/Vault close; deadline expiry revokes future local publication authority, not proof that an already-sent provider mutation stopped. Runtime restart never replays unfinished revocation. Browser process loss does not persist/replay pending OAuth payloads.

## Primary protocol checks and limits

Primary sources were opened on **21 October 2026** and rechecked **22 October 2026**; these support the limited external constraints below, not live EVE acceptance. No provider credentials or live authorization were used.

| Source | Constraint used here |
| --- | --- |
| [Current EVE developer SSO guide](https://developers.eveonline.com/docs/services/sso/) — PKCE and JWT sections | PKCE binds verifier/challenge; state must be verified; authorization code is one-use; application/character/granted scopes come from validated token claims. Discovery provides endpoint locations. |
| [RFC 6749 §§4.1.2, 4.1.3, 6](https://www.rfc-editor.org/rfc/rfc6749.html) | Codes are single-use and bound to client/redirect URI. Refresh responses may replace the refresh token, so loss of a response is not proof the stored token is still safely reusable. Unrecognized authorization-response fields are ignored; duplicates are not accepted as multiple competing values. |
| [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html) | Rotation is one replay-detection mechanism; replay can invalidate the active refresh grant. This motivates conservative uncertain-refresh handling. It does **not** prove EVE currently rotates every request. |
| [RFC 7009 §§2.1–2.2](https://www.rfc-editor.org/rfc/rfc7009.html) | Revocation may affect related tokens/grants. A 200 can also mean the submitted token was already invalid; it does not prove this request uniquely invalidated it. No source here establishes isolation between an old revoke and a later EVE authorization. |

Precise provider error/cooldown behavior, supported token schemas and live SSO grant overlap remain implementation evidence dependencies. Do not assume a token-introspection/read-back facility, request deduplication key or safe POST replay that these sources do not establish. Native Windows/DPAPI, real EVE SSO/roles and extended use remain outside automated acceptance.
