Built-in and extension IDs share `module:<id>` storage. Registry discovery rejects duplicate IDs among discovered descriptors and checks its ID pattern; it does not reject a collision with a built-in catalog ID. The existing [extension contract](../INTERNAL-API.md#registry-descriptor-and-context) tells authors to avoid built-in names. Registry `scopes`/`datasets` are metadata: they do **not** extend built-in collectors or the Auth scope allowlist. The shipped registering extension is [`milestones.mjs`](../../server/modules/milestones.mjs); discovery skips `.mjs` files without a default descriptor. Descriptor loading/validation remains trusted local code, not a plugin sandbox.

### Collection, accounting and output dependencies

- Core admission checks the stored enabled preference; after awaited provider/enrichment work it rechecks connection/scope ownership and the fast pause fence. Still-disabled work suppresses both success/error sample publication and new detail admission; unrelated enabled modules continue. Already dispatched reads are not universally aborted. **Disable then re-enable before completion may reuse a still-current successful read**, preserving its polling deadline and avoiding another request. Module preference revision alone must not invalidate that proven optimization.
- Polling values, samples and freshness survive toggles. Enable does not call `requestSync()`, clear ESI access failures or reset provider cooldowns; ordinary due/cache rules still govern collection. Universe's explicit tick and domain owners have their own dispatch checks. Markets scans, Combat/Session Combat and Universe operations/feeds consult module preferences at their respective boundaries; this trace is not full acceptance of every job/collector interleaving.
- Milestones receives already saved `data.*` observations. An accepted async skill listener may await names and then commit its captured Session accounting after disable removed its subscription. Preserving that accepted work is different from admitting new observations while disabled. Core close drains collection, domain services and bus work, closes Registry, drains cleanup-generated bus work, then closes output/listeners and finally caller-owned storage through the runtime owner.
- Protection treats disabled evidence as unavailable and remains conservative; Stream bindings use relevant module flags. A resulting OBS transition is an external effect with its own unknown/failed outcome ([OBS contract](obs-command-contracts.md)). Stream toast rules/delivery remain outside application-toast consolidation; a module preference receipt must not claim those effects completed.

## Selected target behavior

These draft decisions follow the coordinator's direction and still require completed independent/integrated review before becoming an accepted contract. They are not Build97 capabilities. Reuse the shared protocol without a per-toggle journal or a second collector/lifecycle system.

| Decision | Required owner behavior |
| --- | --- |
| One desired-state entity per module | Validate a complete object, explicit boolean and exact installed module identity; reject unsupported fields/unknown or ambiguous targets before mutation. Authoritative resolution must be unambiguous across catalog and Registry IDs. Bind extension work to the loaded descriptor/version identity; replacement must not let an old request silently act on a different implementation. Keep durable preference revision separate from a process-local activation incarnation. |
| Preference commit | CAS the requested module's base revision and atomically commit desired enabled value, new revision and bound receipt tuple. Different modules do not conflict merely because they share the endpoint/table. Same-value new commits follow the shared revision rule; no duplicate registration/disposal is implied. A conflict performs no fence change, hook, collector dispatch, protection/binding update or invalidation. |
| Exact acknowledgment | Capture the committed module result/revision before any await. Return desired preference outcome separately from activation, retirement and output convergence. Never substitute a later `moduleList()` result for the accepted command's result. Failure after commit cannot mean “not saved”; later superseding intent is also distinct from failure of the earlier effect. |
| Built-in disable/enable | Establish the disabled admission/publication fence in the same synchronous commit boundary, before post-commit follow-up can fail. A storage rollback must leave the prior fence effective. Preserve valid samples/history and current connection/scope checks, unrelated modules, original observation times, provider freshness/cooldowns and eligible off/on read reuse. Polling edits remain a separate policy entity and cannot reactivate disabled collection. |
| One owned extension incarnation | Desired preference may commit while lifecycle application is pending. Retire the prior incarnation before activating another; never accumulate one retiring resource set per click. Disable prevents new tracked deliveries; accepted listener work retains its domain accounting owner. A later enable may commit its preference but waits for the earlier disposer to settle within reviewed bounds. If later intent supersedes it before activation, report that effect as superseded rather than inventing an activation. |
| Hook failure/recovery | Track the latest desired revision and its pending/applied/failed lifecycle outcome. Registration/migration failure performs best-effort tracked cleanup, preserves the primary error and committed preference, and does not repeatedly execute arbitrary trusted hooks on heartbeat, read-back or UI retry. Unresolved cleanup prevents a competing incarnation; late cleanup cannot clear a newer incarnation's state. Require deliberate recovery unless the owning hook has a proved safe, bounded recovery policy. Migration statements/markers and any required atomicity belong to the extension's reviewed synchronous migration contract. |
| Conservative convergence | Disabled protection/binding evidence becomes ineligible immediately; if recomputation fails after preference commit, retain a conservative unavailable/protected state rather than treating the old release-permitting protection or private binding as valid. Rebuild protection, bindings and eligible scheduling from current committed preferences; do not replay the preference PUT. Convergence must not bypass disabled evidence, leak an unsafe reveal or imply actual OBS success. Keep required semantic accounting deduplicated; transient notifications are not an accounting recovery mechanism. Exact Stream/OBS fencing and side-effect failure order require the following OPSEC/Stream contract unit before implementation; preference CAS alone does not secure output. |
| Provider-free read-back | Use authoritative module metadata/receipt and bounded lifecycle status, without calling descriptor `read`, `register`, `migrate`, dispose, Universe tick or any provider. The shared bound tuple proves the preference commit; status separately describes lifecycle convergence. Latest desired value alone cannot attribute a superseded command. No new per-component polling or blind PUT retry. |
| UI ownership/cancellation | Snapshot ID/value/base/command identity at intent acceptance; track pending state per module and response generation. Apply the shared queued-continuation/conflict rules; two tabs cannot silently overwrite each other, while unrelated module operations remain independent. Preserve unresolved intent on lost acknowledgment; switching page/unload is not rollback. Clean UI reads converge by existing private invalidation/reconnect ownership; an older completion must not clear another module's busy/error state. |
| Restart and bounded drain | Normal startup reconstructs current committed module preferences and one supported incarnation per enabled descriptor; durable receipt evidence survives a runtime restart. Interrupted cleanup or arbitrary extension effects do not acquire an exactly-once guarantee. Hook initialization/migration must own restart safety; a known unresolved non-idempotent failure needs deliberate recovery, not automatic repetition. Shutdown stops new work, retains ownership of accepted accounting/cleanup and reports a failed handoff if it cannot drain. |

Feasibility and limits: SQLite can atomically store preference/revision/receipt; an existing Core fence or Registry lifecycle owner can apply it without a global async mutation queue. Timers can bound cooperative asynchronous waits, **not preempt blocking synchronous trusted hooks**. Neither SQL rollback nor a timeout reverses arbitrary extension effects. The implementation must identify safe hook recovery versus unresolved state explicitly, with bounded metadata rather than an unbounded operation log. An interrupted cleanup that later resolves remains owned; declaring a deadline must not silently free its slot and start a competing incarnation.

## Cost and continuation

Current ordinary built-in toggle performs one preference UPSERT plus protection/binding/invalidation work, serializes the complete module list, then the browser reloads bootstrap. There is no catalog-wide snapshot rewrite or direct `requestSync` call. Universe adds its tick; OPSEC changes may generate a semantic event and OBS work. Extension hooks can have independent costs; cleanup error history is bounded at 20 but pending cleanup count/wait is not capped by this code. These are source bounds, not measured performance acceptance.

P0-04 must settle aggregate command/read capacity and payload bytes, per-extension lifecycle admission/retirement limits, cooperative cleanup deadlines, receipt/status bytes, event/provider bounds and measured latency/memory variance. Preserve existing metadata-only checks, scoped projection and cached-read reuse. P0-03 owns diagnostics and application-toast presentation. Full descriptor/startup contract auditing (C03.4/C05), each collector algorithm (C03), remaining jobs/commands, extension read-through effects and OPSEC/Stream convergence ordering remain explicit successors; this document does not close them. No corresponding implementation starts before those dependencies and budgets are reviewed.
