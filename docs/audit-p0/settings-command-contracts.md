## Observed current ownership and boundaries

Shared transport: [`model.ts:api()`](../../components/kairo/model.ts) sends same-origin JSON/CSRF, awaits `fetch` then JSON parsing, rejects malformed JSON/non-2xx, and supplies no retry, request timeout, AbortSignal, revision or command identity. A well-formed success body is not schema-validated here. A transport failure or unreadable success response does not identify the write outcome.

[`index.mjs`](../../server/index.mjs) checks stopping, local Host, session/Origin and mutation CSRF before the handler. `body()` requires JSON content type, counts up to 150,000 raw bytes and parses the complete body; it is not an object/field schema validator. Handler promises are tracked for shutdown even if sockets disappear; accepted work drains before Core/Store close. The handler does not tie an already-parsed write to client cancellation. Errors map to HTTP 400 except explicit domain 409, unless headers were already sent. A 400 therefore does not generally prove that no write occurred.

Store details: [`store.mjs`](../../server/store.mjs) owns one SQLite connection with WAL and 3,000 ms busy timeout; `set()` is one prepared UPSERT and leaves atomic grouping to callers. `saveSnapshot()` increments an in-memory UI delivery token after SQL success; those tokens are neither transaction versions nor command receipts. Both settings routes execute their post-body local work synchronously, so separate request handlers cannot interleave at an `await` inside that section. Different tabs still reach that section in server execution order, which need not match human intent time. Synchronous execution does **not** make several SQL statements atomic against failures/crash.

Polling effects require separate reasoning: the durable policy write precedes every derived snapshot rewrite and projection/invalidation. No encompassing SQL transaction/rollback restores earlier changes if a later step throws. The GET may therefore show a committed new policy after a failed PUT response, without proving that every dependent deadline/output converged. The existing validation test's word “atomically” concerns rejecting invalid intervals before any write; it is not storage-fault atomicity proof. Actual partial-failure and restart behavior remain untested by this unit.

`refreshDeadline()` keeps provider expiry as a lower bound, uses original observation time rather than Save time, and considers skill/queue completion. `pollingPolicy()` preserves strict protection overrides. `savePolling()` itself does not call provider fetch; it changes subsequent scheduling and refreshes local protection/bindings. Delayed publication is not permission to bypass provider cooldowns or resubmit the preference write.

## Selected target contract for implementation

These decisions follow the [shared P0-02A contract](command-contracts.md). Storage/wire encoding remains an implementation choice; the externally observable guarantees do not.

| Decision | Required behavior and owning boundary |
| --- | --- |
| Separate authoritative entities | `theme`, `clientId` and the **complete polling policy** each have an authoritative revision. Theme and Client ID do not conflict merely because they share an endpoint. Polling remains a whole-policy replacement: it must not silently merge a stale editor's unrelated old values into a newer policy. Revisions survive runtime restart and cannot match a freshly initialized profile by accident; use the shared storage-lineage rule. Every successful new commit advances revision, including a same-value request. |
| Strict, complete validation before admission to commit | Validate the full envelope and every supplied value before changing any entity. Theme is an allowed string; Client ID is an explicit string with the current format/connected-roster restriction; polling preserves exact choice lists and reset semantics. Unknown/unsupported input must not be represented as a successful requested change. Decide precise error wording and compatible envelope encoding during implementation, with acceptance tests. |
| Compare-and-swap at the runtime owner | Each supplied entity must match its expected revision at commit time. A stale write returns conflict before storage, scheduling, invalidation or external effects; it cannot silently overwrite newer state. No client timestamp or browser-queue ordering is treated as authoritative. Client ID's roster restriction is rechecked in that same commit section. |
| Atomic multi-entity requests | If `/settings` continues to accept both fields, validate/check all supplied entities then commit all requested values, revisions and commit tokens in one transaction; otherwise reject the whole composite request. Never acknowledge one field while silently ignoring or failing another. No selected requirement forces a bulk endpoint; retaining it must satisfy this all-or-nothing contract. |
| Exact command result | A successful local commit returns its canonical result and revision, even if a later command changes the current state before response delivery. Bind a last-commit command token to each entity atomically with its revision/value, following the shared owner, storage-lineage, expected-revision and immutable-payload binding. A matching bound receipt tuple (entity, lineage, token, base and result revisions) can prove that command committed; bare token equality cannot. A different token proves **neither** that it never committed nor that it was rolled back. The bounded token is not a promise of idempotency or a replay endpoint; a repeated current token cannot authorize a new commit. Wire encoding belongs to implementation. |
| Commit versus convergence | For polling, authoritative policy acceptance is distinct from application of derived deadlines, protection/bindings and UI invalidation. A stale conflict must perform none of these effects. After policy commit, failure in derived application/publication must preserve the committed identity and an explicit recoverable convergence outcome; do not mislabel it as “not saved.” Reconcile/reapply derived work from authoritative policy without issuing another user mutation. Prove restart convergence on a fresh synthetic profile. |
| UI ownership and conflicts | Keep same-document ordered accepted writes, immutable payloads and newer draft guards. Associate response/read-back with the submitted command/editor generation. A queued continuation may adopt the exact successful predecessor revision only when it was explicitly accepted as a continuation on the same entity/base; it must not silently rebase over another tab. Unknown/conflict pauses successors and retains their draft/intent. On conflict, read current authoritative state, retain the user's unsaved draft, and require an explicit new intent to overwrite. Choosing an unrelated theme must not erase Client ID edits. A newer draft is not automatically replaced merely because the old write committed. |
| Unknown outcome and bounded reconciliation | A lost/invalid acknowledgment or server error after dispatch is potentially unknown. Retain draft/submitted intent and make **one initial authoritative read** including the bound receipt tuple; never blindly repeat PUT. A matching bound entity/lineage/token/base/result tuple resolves commit; a different token/latest value may establish present state but not the earlier command's history. An unchanged old revision cannot prove rejection while accepted work may still commit. If the read cannot settle the result, preserve uncertainty and allow deliberate later inspection. Read-back must not trigger provider traffic. Concrete read deadlines/capacity must be fixed before implementation alongside P0 budgets; no infinite background reconciliation. |
| Tab/restart convergence | Prefer existing private invalidation/reconnect ownership, with setting-entity revisions; do not add per-component polling. Apply only newer authoritative settings to clean editors, preserve dirty drafts and recover after a runtime epoch change. Accepted server work remains owned during shutdown; a browser unload/cancel does not roll it back. Unsent browser-queue entries are not durable server admissions and must not be described as saved after page loss. |

Feasibility: existing synchronous SQLite owners permit transactional compare-and-swap without a new global async write queue. A per-entity revision/token prevents unrelated-setting contention and keeps stored command history bounded. Polling's authoritative policy can be committed atomically; changing in-memory policy/`nextRun`, writing derived snapshots and publishing protection/output must have a separately specified failure/recovery order. Wrapping SQL alone does not roll back in-memory state or emitted output. The shared storage/publication owner must settle that order before changes; this document does not prescribe an unmeasured full-snapshot rewrite or a second notification architecture.

Next behavioral units must retain expected persisted values, in-memory policy, deadlines/projections, emitted invalidations and request counts at controlled barriers:

1. Validation and atomic setting commit: missing/extra/non-object fields, wrong scalar types, invalid second composite field, connected-roster changes, first/second-statement storage failure, busy timeout and crash between planned markers. Confirm no partial commit or premature success under the selected contract.
2. Concurrent intents: two tabs edit the same entity, two tabs edit disjoint entities, stale full polling policies, newer command committed before older response, same value with different revisions, queued remount/rejection and explicit overwrite after conflict. Use barriers and a revision oracle, not client clock ordering.
3. Unknown outcomes: disconnect before body completion, after parsed body, after commit/before acknowledgment; malformed successful JSON; application success followed by bootstrap failure; process replacement before/after commit. Read-back/token proves only what the result supports, and no automatic second PUT occurs.
4. Polling convergence: fail the first/middle/last derived snapshot write, protection/binding evaluation and SSE delivery separately; restart and recover from authoritative policy. Failed application must not create a false rollback claim or destroy provider cooldown/failed-sample state. Include healthy controls and multiple connected pilots/shared datasets.
5. Chrome/Firefox editors: cross-tab conflict and reconnect, clean versus newer dirty draft, source/response owner teardown, clear saved-versus-unknown status, keyboard/narrow layouts and bounded reads. This design unit runs none of these gates.

## Cost model and deferred boundaries

Current per-single-field setting Save: one settings UPSERT, plus a browser bootstrap read after successful PUT; no direct provider request. Client ID Connect may add its explicitly selected persist then Auth request, whose identity/side effects are a later C01 unit. Composite current settings can perform two UPSERTs; target atomicity adds no reason to double request count.

Current polling Save: one authoritative preference UPSERT; at most `9 + 29 × N` catalog sample visits for `N` connected pilots, with writes only for eligible ready/timestamped samples and additional queue reads for applicable samples. Local protection/binding work and generic invalidation follow; browser adds state refresh after success. These are source-derived operation bounds, **not measured latency/memory budgets** or proof of optimal cost. Existing [polling cadence tests](../../tests/kairo/esi-optimization.test.mjs) remain controls. Measure fresh profiles with zero/one/many pilots, ready/mixed snapshots, ordinary and concurrent settings traffic before accepting overhead changes. Provider limits/cooldowns must stay effective; command reconciliation must not add provider traffic.

Still deferred: exact revision/token wire encoding and byte limits; numerical reconciliation deadlines/capacity and tab-flood limits; a measured comparison of derived-snapshot versus lazy-deadline application; detailed settings invalidation payload and UI conflict presentation; native/live verification. These are required follow-on decisions/gates before corresponding implementation, not waived scope. P0-03 owns diagnostics/toast design; P0-04 owns measured budgets. No settings retry implementation or storage redesign is banked by this document.
